# WATA — AGENTS.md

## Project

Automated trading assistant for Saxo Bank Knock-out warrants (Turbos). Python 3.14, FastAPI, async microservices in Docker.

## Service map

| Role               | Entrypoint (`__init__.py`) | Communicates via                          |
|--------------------|-----------------------------|-------------------------------------------|
| `web_server`       | `src/web_server/`           | FastAPI on `:80`, query-param token auth  |
| `trader`           | `src/trader/`               | HTTP-polls web_server `/latest-signals`; hands what it could not sell to `trading-ops` |
| `position_monitor` | `src/position_monitor/`     | Saxo WebSocket streaming + `trading-ops`; the index's quotes from `wata.prices` while `index_between_quotes` |
| `scheduler`        | `src/scheduler/`            | Publishes to `trading-ops` / web_server   |
| `telegram`         | `src/mq_telegram/`          | Consumes `telegram` queue; answers the bot's read-only commands (`reporting.telegram_commands`) |
| `watchlist_manager`| `src/watchlist_manager/`    | REST API on `:8081`                       |
| `admin`            | `src/admin/`                | FastAPI on `:8082`, cookie session; serves the React UI built from `admin_ui/`; its AI agent calls the Claude API; LuxAlgo's MCP tools while `admin.luxalgo_enabled` |
| `price_recorder`   | `src/price_recorder/`       | Own Saxo stream; writes PostgreSQL only. Nothing calls it |
| `capital_feed`     | `src/capital_feed/`         | Own Capital.com stream; writes PostgreSQL, publishes live prices to RabbitMQ `wata.prices`. Nothing calls it |
| `ta_engine`        | `src/ta_engine/`            | Reads the Capital.com feed's tables; runs the signal rules' Pine scripts in a confined Node child; POSTs live rules' signals to web_server `/internal/signal` (Bearer). Nothing calls it |
| `service_control`  | `src/service_control/`      | FastAPI on `:8090` of `control-net`, which only the admin joins (Bearer, a compose secret); holds Docker's socket to restart WATA's own containers |

Each service runs as a Docker container; `WATA_APP_ROLE` env var selects which `__init__.py` runs via `src/start_python_script.sh`.

## Infrastructure

- **RabbitMQ** — queues: `trading-signals` (trade actions, no longer consumed), `trading-ops` (ops/daily_stats, and the closes the admin asks and the trader hands over), `telegram_channel` (notifications); topic exchange `wata.prices` (the Capital.com feed's live quotes and bars, transient, read by the admin while a chart follows them, and by the position monitor while `position_management.index_between_quotes`)
- **PostgreSQL 16** — replaces DuckDB (migrated in v0.7.0). DuckDB config is dead. Dumped by `pg_backup1` (`deploy/pg_backup.sh`): each night at 02:17 UTC without the bars' rows, whole on Sundays, 14 and 4 kept in `var/lib/backups` (`last.json` for the admin's health, read-only), pulled to the Mac by `lab/sync.sh`; `docker exec pg_backup1 sh /pg_backup.sh check` restores the newest into a scratch database and counts the trading tables. With `BACKUP_AGE_RECIPIENT` and `BACKUP_S3_BUCKET` in `.env`, each dump is also encrypted with age to the operator's public key (its private half stays on the Mac) and sent with rclone to an S3-compatible bucket, 14 nightly and 8 Sunday copies kept there (`last.json`'s `offsite`; health warns after two nights without a copy sent); the image is `wata-backup:<version>` (`deploy/pg_backup.Dockerfile`, age and rclone pinned by version and sha256, and the script copied in, built by `docker_build.sh` from those two files alone; its build arguments are `PINNED_*`, since rclone takes any `RCLONE_<flag>` of its environment for that flag, and `RCLONE_VERSION` was read as `--version`), and nothing on the server can decrypt. `python -m lab backup check [--offsite]` restores the newest dump, or the bucket's newest copy, on the Mac and counts the same tables. Out of memory, the kernel kills the admin and the backups before the trading path (`oom_score_adj`, `tests/test_deploy_compose.py`). Its container has 1536M, `shared_buffers` 512MB, `effective_cache_size` 1GB, `work_mem` 16MB and a `/dev/shm` of 256m (`command` and `shm_size` in the compose file, held by `tests/test_deploy_compose.py`), for a server of 8 GB: a change of them restarts the database, so it waits for a closed market.
- **Traefik** — reverse proxy, Let's Encrypt, TradingView IP allowlist
- **The disk** — one ext4 root of 96 GB holds everything (2026-11-17: 13 GB used; PostgreSQL 0.9 GB, the recorder's bars about 35 MB a trading day; 2026-11-19: Docker 8.6 GB in `/var/lib/containerd`, the containerd image store, Docker 29.9). `watadisk.timer` (made by `install_package.sh`) samples it every hour on the host, at the lowest priority (`src/disk/collect.py`, the server's own python3, stdlib), into `var/disk` (`samples.jsonl`, 14 days; `latest.json`), its own folder, which no container mounts, then copied to `var/lib/disk`, which the admin mounts read-only and the scheduler reads through `var/lib`. Five containers write in `var/lib` as root, so the collector, root on the host, never reads `var/lib/disk` (but once, to take the samples kept there before) and writes there only to a name of its own made by `O_EXCL`, renamed over the old file: a link left there is replaced, never written through (`open_folder`, `_write`, `_read`: a plain file only, never through a link, nor a pipe or a device)
- **Config** — JSON at `WATA_CONFIG_PATH` path, validated strictly by `ConfigurationManager`

## Testing quirks

- **`WATA_CONFIG_PATH` must be set** before importing `src.web_server` (tests set `os.environ["WATA_CONFIG_PATH"] = "tests/test_config.json"`)
- Test config at `tests/test_config.json` — omit `day_trading` rule if testing with `trading_mode != "day_trading"`
- `tests/test_web_server.py` patches `verify_token` and `Request.client` for IP filtering tests
- `tests/test_config.json` uses minimal rule set; adding more rules requires updating config
- Some tests run the real Pine runner and need Node 22+ on the PATH (Node 24 through nvm) and `runner.mjs` built; they are skipped otherwise
- The tests replace PostgreSQL with fakes that only record the SQL text. New SQL can be run for real without Docker: `pip install pgserver asyncpg` in a throwaway virtual environment gives a PostgreSQL 16 in a folder (`pgserver.get_server(path).get_uri()`), which `PostgresConnectionManager`, `init_schema` and the managers accept as they are
- **`tests/test_infrastructure_live.py` is the database and the queue for real**, through the services' own code. It is skipped unless given `WATA_TEST_POSTGRES_DSN` and `WATA_TEST_RABBITMQ` (`user:password@host`), and must be run on its own: in a run of all the tests, other files have already put an empty module in the place of `asyncpg` and `aio_pika`. CI runs it against a PostgreSQL and a RabbitMQ of its own. Only for ones that can be thrown away: its messages go to the queues the services read
- **The stream client's connection is tested against a WebSocket server on the machine** (`LocalSaxoStream` in `tests/test_saxo_streaming_client.py`): opening, reading, Saxo dropping the connection, coming back with the last message read, leaving. Those tests are what says whether an upgrade of `websockets` keeps the position monitor's link to Saxo working: run them before and after one
- **No test ends a process with a signal that dumps core** (`os.abort()`, SIGSEGV, SIGBUS…): on a Mac each one is a crash report, and a dialog asking the user about it (one fake runner made 39 of them before v0.80.0). A child that must die is killed (SIGKILL); what a signal means is `exit_said`'s own test (`src/price_history/process.py`). The same goes for a probe that runs Node out of heap on purpose: say so first.

## Architecture notes

- **Trader does NOT consume RabbitMQ** for trade signals — it long-polls `web_server:80/latest-signals` via `SignalPollingClient`. Old RabbitMQ `trading-signals` queue consumption was removed.
- **Signals are executed once.** The web_server store keeps the latest signal per indice until a newer one replaces it, so the trader dedups on `signal_uuid` (`select_signals_to_dispatch` in `src/trader/__init__.py`). An internal signal sent again under its key (the TA engine's, when the web server gave it no answer) keeps the `signal_uuid` it was first stored under (`TakenKeys`, below under the TA engine).
- **No entry around US releases** (the optional `macro_news` rule of `trade.rules`, off unless it is there): from `minutes_before` a release to `minutes_after` it (`minutes_after_fomc` for an FOMC statement, whose press conference follows), for the releases its `events` name (FOMC, CPI, NFP and PCE unless it names others, `DEFAULT_EVENTS`; PPI, RETAIL, GDP and JOLTS, kept from late 2026, only once named); with `flatten_minutes_before` (0 unless given) the position monitor also sells what is held from then (see below). The calendar is `src/trade/data/macro_calendar.csv`, read by `src/trade/macro_calendar.py` (`NewsRule`, `window_at`, `refusal_text`): the trader reads it, so it lives on the trading side, and the backtests import it from there (never the other way). New York's hours, whatever either side's clocks. `TradingRule.check_macro_news` runs right after `check_market_hours`; an unreadable calendar never stops the trader. Past the calendar's last known day of the releases the rule names nothing is known and entries go on; from 30 days before it, the scheduler says so on Telegram each morning and the admin's health has a warning (`upkeep`, which names the kind that ends first). Each kind is known from its first row (`Calendar.since`, `known_from`): a backtest that names a kind on days before it says so. ISM's manufacturing index is not kept: only its rule is public, its dated calendar is for ISM's members. `ConfigurationManager` checks the rule only when it is there.
- **One moment, one trade: an entry wins over a close of the same moment.** An entry sells the other side before it buys, and a close taken after it would sell the position just opened. The TA engine and the replays (backtests, studies) send only the entry of a bar that raised both, the close journaled or listed as no signal with why (`settled` in `src/ta_engine/signals.py`); the web server's store does not let a `close-position` replace an entry of the same `signal_timestamp` (`SignalStore.upsert`, TradingView's alerts), while an entry still replaces a close. The scheduler's close is stored under `n/a`, apart.
- **An entry refused against a position still sells it** (`src/trade/refused_entry.py`, pure, shared by the trader and the simulator, in `_CODE`; `position_management.close_on_refused_entry`, on unless false, checked by `ConfigurationManager`; since v0.105.0): an entry taken sells the other side before it buys, and the exit of a bar that also raised an entry is never sent, so an entry the trader refused left the position open against the strategy. Of the 19 exits the live rule raised on 22-27 Nov 2026, 10 came with an entry, of which 6 were refused and 2 failed (no position was held then).
  - **What is sold**: the positions of the other direction alone (`OTHER_SIDE`, `close_managed_positions_by_criteria(action_filter=<side>, defer_bookkeeping=True)`, so `Explicit Close (long)` or `(short)`), never "All": the pause is checked before the duplicate, and a refused "Resume Long" while long must sell nothing.
  - **When**: the refusal is a `TradingRuleViolation` and the signal itself stands (`signal_stands` in `src/trader/__init__.py`: its age, its index and its confidence checked again, an earlier check having refused before the last two were read). Hours, a US release, the pause, a guard, Saxo's login, the day's result, the cooldown, the day's trades and the breakers sell; a signal too old, under the confidence wanted or for another index sells nothing. An entry that fails after its checks is as before (the classic mode has sold already, a cash reserve sells then).
  - **How** (`sell_other_side`, called from `handle_trading_signal`'s `except TradingRuleViolation`): the open positions read first (none the other way: nothing more is done, the refusal as before and silent), the sale, what was not sold handed to the position monitor (`hand_over_unsold`), the balance read again and no reading left standing (`invalidate_spending_power`, `flat_balance.moved()`). It never raises: the signal stays `refused` whatever becomes of the sale. The journal row is written after the sale (the signal page reads the trader's sales up to it), its reason the refusal then what was sold (`said`, `not_sold`); Telegram says it only when something was sold or could not be. Not a check: `rehearsal_steps` is unchanged.
  - **The simulator** (`_sell_other_side` in `src/backtest/simulator.py`, `signal_stands` in `src/backtest/rules.py`, built from the predicates `entry_refusal` uses): the same sale an order's time after the refusal, as `_close_signal` sells, the signal `refused` with the same text and its `closed_trade_ids`. The setting `close_on_refused_entry` (group exits, off for the runs made before, `from_config` on unless false). Parity tested (`test_a_refused_entry_sells_the_other_side_as_live`).
- **Position Monitor** uses Saxo WebSocket streaming (replaces old 7s REST polling). Still consumes `trading-ops` for `daily_stats` and fallback `check_positions_on_saxo_api`.
- **Stream reader and position checks are decoupled.** `SaxoStreamClient` only merges deltas and flags a change; a separate task calls the callback with the latest snapshot (updates during a slow callback are coalesced). Don't await slow work in the receive loop.
- **The price subscriptions Saxo asks to have made again are made in a task of their own** (`_resetsubscriptions`; `_ask_info_price_resets`, `_reset_info_prices` in `src/saxo_streaming/client.py`, since v0.100.0): one after the other, the old one removed, then the one desired now created, while the receive loop goes on reading the others' quotes. Saxo often asks twice in a row: one that waits for its turn is made again once; for the one being made again, a request read before its old subscription's removal was answered can only be about that old one, and one read later makes it again once more. What Saxo sends of the new one before its snapshot is read is applied after it, in order (`_reset_held`); `_sync_desired_info_price_subscriptions` leaves the one being made again to the task; one that cannot be made again is said and left to the next synchronisation. Until then the reset was awaited in the receive loop: on 3, 5 and 9 Nov 2026 the watchlist manager made its four subscriptions again twice within half a second (16 requests), Saxo refused one (429, no limit named, so waited 60 s), and it read no quote for a minute, while the trader took its watchlist for current (a watchlist is stale by its candidates' age, not its quotes'). The position subscription is still made again in the receive loop: its snapshot replaces the positions held, and an update read before it would be lost under it; a monitor whose stream is silent for 15 s checks its positions by REST.
- **A position Saxo sold leaves the stream by Saxo's deletion** (`SAXO_DELETED` in `src/saxo_streaming/client.py`): Saxo removes an item from a list subscription with its key and `"__meta_deleted": true` (its own client library's `OPENAPI_DELETE_PROPERTY`), never with a `Status` of Closed on this account (no such line in the monitor's logs since August 2026). Until v0.99.1 the client merged it as a field: on 2026-11-23 position 7829220002, sold at 08:42:53 UTC, stayed in the snapshot with `CanBeClosed: true`, its sale was tried again 100 times (`NotOwned`) and it was "adopted" every 90 s. The periodic reconciliation (`StreamPositionHandler.reconcile` without ids) also checks the stream's list against Saxo's REST answer, read once while the stream lists anything: a position Saxo does not hold (`held_at_saxo`: absent, or listed as Closed or Closing) and that Saxo's closed positions name is dropped from the stream (`SaxoStreamClient.forget_positions`); one Saxo's answer does not list yet but that no closure names (just bought) is kept. All of it outside `src/trade/async_services.py`, which every backtest's code digest holds.
- **Closures are recorded in the background** (`_record_closed_position_in_background`); `_closing_position_ids` keeps a position from being sold twice meanwhile. DB↔Saxo reconciliation (`StreamPositionHandler`) runs when a position leaves the stream and on a timer, not per tick.
- **A sale is kept until Saxo no longer lists the position** (`src/trade/close_intents.py`, pure, in `AsyncPerformanceMonitor`): an exit decided, a close asked from the admin (`request_close`), and what the trader could not sell (`not_closed` of `close_managed_positions_by_criteria`, handed over as a `close_position` ops message with its `reason`, `src/trade/ops_queue.py`) become intents, tried again with growing waits (`retry_after`), said on Telegram less and less often (`ALERT_GAPS`), ended when the position leaves the stream (Saxo's deletion, or the reconciliation's check, above). A first, urgent attempt (a threshold just hit) asks nothing of Saxo before its sale; any other first looks for a sale already working at Saxo (`get_open_orders`) and waits for it: a second sell is refused (`SellOrdersAlreadyExistForOwnedContracts`). The monitor tries them every second (`keep_flat`, on the stream's last snapshot): an issuer that stops quoting brings no stream update. A close never skips a position in silence: `CanBeClosed: false` is `not_closed`, a position Saxo does not list `not_listed`, journaled as such.
- **Nothing is held after the day's close nor into a US release**: from `close_position_time` + 60 s until the next day's `trading_start_hour` the monitor sells what it still manages (`END_OF_DAY_REASON`, said once per position), and from the `macro_news` rule's `flatten_minutes_before` a release until its window ends (`flat_window_at`, reason `Flat before CPI (14:30)`, mirrored by the simulator, `tests/test_backtest_parity.py`). Entries are refused from the earlier of the two starts (`NewsRule.window`). Two Friday positions were held over the weekend (18 Sep, 9 Oct 2026) and a long held through the CPI of 14 Oct, unquoted for 250 s, was sold at −30 %.
- **A position just bought is judged from Saxo's next quote** (`src/trade/fresh_quote.py`, pure, shared by the monitor and the simulator; `position_management.wait_for_fresh_quote`, on unless false, checked by `ConfigurationManager`): Saxo quotes a turbo about every 30 s (40 at the 95th percentile, 13-20 Oct 2026) and fills an order at the live price, so the bid standing when a position appears is often older than its purchase. A position first seen within `FRESH_AFTER_SECONDS` (120) of its opening (`PositionBase.ExecutionTimeOpen`) is not judged on its bid until that bid changes: no stop, take-profit, trailing stop or daily target, its best result not raised; what comes with time (the day's close, a US release) is sold whatever the quote. A position whose opening is unknown is judged at once, as before. On 19 Oct 2026 a stop was "hit at -8.47 %" on a bid 17 to 27 s older than the purchase and sold at +0.51 %; six daily targets were "met" 1 to 6 s after a purchase and sold at a loss.
- **Between Saxo's quotes, a position may be judged on the index** (`src/trade/index_estimate.py`, pure, shared by the monitor and the simulator, in `_CODE`; `position_management.index_between_quotes`, off unless true, checked by `ConfigurationManager`):
  - The estimate is Saxo's last bid plus the turbo's euros per index point times the index's move since that quote (`BetweenQuotes`, `TurboSensitivity`): learned from its own quote changes against the index (the median of its last moves of 8 points or more, 5 needed), until then a prior of 0.0086 € a point (0.01 $ at the euro's rate) believed only below the bid's price per point of distance to its barrier at that quote (the barrier is read from the turbo's description, `parse_saxo_turbo_description`): never read from the barrier, a TurboXL's financing level not being its knock-out level. Measured on 8 turbos of 26-30 Oct 2026 (57,468 pairs of quotes): 0.120 % from Saxo's next quote at the median and 0.589 % at the 95th percentile, Saxo's standing bid 0.253 % and 1.371 %.
  - The index is the Capital.com feed's instrument of the one indice the trader takes (`followed_epic`; none with several: a position does not say its indice; a feed section that names no instrument counts the feed's own default, US100 labelled us100, `feed_instruments`, held to `src/capital_feed/settings.py` by `tests/test_index_estimate.py`: until v0.85.0 such a section, the server's, followed no index, live and in the backtests, and the setting did nothing), its quotes read from `wata.prices` by an exclusive queue of the monitor's own on a channel of its own, without acknowledgements, into `IndexQuotes` (`src/trade/index_feed.py`, which imports nothing of the feed: its exchange and keys are held to the feed's by `tests/test_index_between_quotes.py`). Nothing is awaited for it; a failure to follow it leaves the exits on Saxo's quotes.
  - Saxo's new quote of a position it may be judged on (bid or ask changed, `_note_quote` in `_evaluate_positions`) is the anchor, with the index then when fresh. Each second, `keep_flat` runs `judge_between_quotes` first: on the managed state read last (no database), for each position not waiting for a fresh quote, not already to be sold, it judges every price exit (`_price_exit`, the one function both paths call) on the estimate. Refused without a quote of the index in the last 2 s (`INDEX_FRESH_SECONDS`), the index unknown at Saxo's last quote, Saxo's quote older than 90 s, the index at its barrier, or an estimate more than 25 % from Saxo's bid. A sale is urgent, its stop-loss starts the cooldown, its reason the exit's own then `; US100 between quotes: <estimate> from <Saxo's bid>, <age> s` (held to the 128 characters of `position_close_reason`): its group on the Exits page is kept, and the page's "By what decided the exit" counts them (`decided_on` in `src/admin/live_breakdowns.py`). The best and the worst stay Saxo's quotes.
  - The monitor's heartbeat says the index followed and its newest quote (`index_between_quotes` of its figures); health warns when it is on with no index followed, or no quote of it for 15 s in trading hours (`INDEX_QUOTE_STALE_SECONDS`). The save preview warns when it is switched on without an index to follow.
  - The simulator (`_judged_between_quotes`, `_note_quote` in `src/backtest/simulator.py`), with the setting (`index_between_quotes`, off for the runs made before) and the index the monitor would follow (`index_epic`, from the configuration), on the feed's bars of each day (`IndexSeries`, the middle of bid and ask, the buckets without a quote left out, `DayData.index`): a turbo's quote taken to come in the middle of its ten seconds, the index read there; in ten seconds without one, the estimate judged at the index's open, low, high and close (the nearer to its close last), at its open alone in those with one; sold at the estimate that decided it as at a quote (`stop_fill`, a take-profit never better than its level), measured fills adding their delay and slippage. Parity tested (`tests/test_backtest_parity.py`).
- **A purchase Saxo refuses for funds is sent again with fewer turbos** (`src/trade/funds_retry.py`, pure, shared by the trader and the simulator, in `_CODE`; `trade.config.buying_power.safety_margins.funds_retry_percent`, 4 unless set, 0 for none, and `funds_retries`, 2 unless set, checked by `ConfigurationManager`): WATA sizes an order on the turbo's last quote, which Saxo sends about every 30 s, while Saxo checks the cash at its live price, a few percent dearer in a fast market. Once Saxo refuses an order with `InsufficientFunds` (`refused_for_funds` of `src/trade/exceptions.py`: under `ErrorInfo` or at the top level; WATA's own sizing refusal is not one), `execute_trade_signal` sizes it again on the ask it chose the turbo on raised by `percent` × the attempt (4 %, then 8 %), always fewer turbos than the order refused (`next_amount`), and sends it once more (`_amount_after_refusal`; the pacer spaces them, each its own request id and row of `order_request`, its context's reason saying why). Any other refusal is raised as before. The trade's Telegram message says it. The backtest of 15 Oct-11 Nov 2026 (run 20261111-130923-8c1c4c) had 22 of its 54 orders refused so, filled 0.7 to 13.9 % above the ask they were sized on: at 4 % and twice, 21 were bought with 96 to 98 % of the account. Live orders of 3 to 5 turbos (one turbo aside, 20 to 33 % of the order) were never refused for funds. Parity tested (`tests/test_backtest_parity.py`).

- **A service runs its main coroutine with `event_loop.run(main())`** (`src/event_loop.py`): on uvloop, as the loop of that run alone. `uvloop.install()` goes through asyncio's policies, which Python 3.14 deprecates and 3.16 removes. The servers started by `uvicorn.run` get uvloop from uvicorn itself.
- **`websockets.connect` is the library's asyncio client** (the default one since websockets 14): a connection has a `state`, no `closed`, and `ConnectionClosed` says what was received in `rcvd`. `SaxoStreamClient` passes `proxy=None`: that client would otherwise look for a proxy in the environment, which the one before never did.
- **A deploy recreates only what a release changes** (`src/release/`, since v0.61.0; `watadeploy` on the server):
  - **Installing stops nothing**: `install_package.sh` builds `wata-base:<version>` and `wata-backup:<version>` beside the running images (`docker_build.sh`, only when that version with that content is not built yet, its label `wata.content`), checks the image (`src/release/check.py`, in it, on the server's `config.json`, without network: CI's checks), and only then writes `/app/wata/VERSION`, the newest release, whose compose files every command uses. `latest` is never moved again.
  - **Each container runs the image its pin names**: `/app/wata/release/images.env` (`WATA_IMAGE_<CONTAINER>=wata-base:<version>`, `pin_variable`), read after `.env` by every compose command (`--env-file` twice), outside every container. Only `watadeploy` changes a pin, recreating that container alone (`up -d --no-deps --force-recreate --pull never`); `watastart` is `up -d --no-recreate`. The first install pins each running container to the image it runs, tagged with its own `/app/VERSION` (`bootstrap`), so that the switch recreated nothing. No container mounts a file of a release's folder (`tests/test_deploy_compose.py`): the backups' script is in their image.
  - **What changes** is read inside each image (`src/release/manifest.py`, stdlib only, fed on stdin to the image's Python, so it also reads images built before it; cached by image id in `release/manifests/`): a container's code is every file its entry can load (imports at module level and in functions, parents, relative imports; another service's entry file for its module level alone; `-m` targets named in strings; `DYNAMIC`, the one `import_module`; `DATA`, the files the modules read, the built `static/`, `runner/` and `checker/` included), compared as syntax trees (comments and layout change nothing); its libraries the distributions its imports need (`importlib.metadata`, requirements followed); the platform (Python, Node, the system's packages) alone is optional. **A non-Python file added under `src/`, a module loaded by name, or a new `docker exec` of a module fails `tests/test_release_manifest.py` until declared**; the CI image job checks that what each entry loads stays inside its static closure. The server's commands (watasaxoauth, watawebtoken, the admin's CLI, wataprices, `watavault export-saxo`) run in a container of their own on the newest image (`watatool`, `compose run --rm --no-deps --label traefik.enable=false`): with `docker exec` they ran the service's image, and brought their files into its closure (`watawebtoken` brought `src/database/postgres.py` into the web server's).
  - **The plan** (`src/release/plan.py`, pure): unchanged, change (code, libraries, compose definition compared with the files that created the container, its label, without the image and `depends_on`, or the image's own settings), optional (platform), infrastructure (Traefik, PostgreSQL, RabbitMQ: only `watadeploy full`), absent. Containers that change because of the same file form a group that moves together; a group goes now when none of its members is held back.
  - **Guards** are the admin's restart guards, moved to `src/release/guards.py` (stdlib, zoneinfo; `src/admin/service_restart.py` and `src/admin/downloads.py` import them back, `tests/test_release_guards.py` holds the answers to pytz's), plus `deploy_refusal`: the price recorder and the Capital.com feed wait for WATA's market to close (the operator's choice, 2026-10-29). The market is open, for a restart and a deploy, by `may_trade` (since v0.104.1): WATA's hours on a weekday (`market_is_open`), less the days the trader takes no entry on (the configuration's `market_closed_dates` and the US market's holidays, read on the day of the market's hours as `check_market_hours` reads them) and what follows the close of a day the US market closes early. The calendar is the trader's file, read again with the standard library (`market_days`: `src/trade/market_calendar.py` needs pytz, which the server's python3 has not), held to the trader's reader and to its answers by `tests/test_release_guards.py`; a file that cannot be read leaves the hours alone. `market_is_open` itself stays the hours alone: what waits for the day's close (paper days, nightly runs, the debrief, the downloads, the export) has nothing to do on a holiday that it would not do in the evening. Until then a US holiday counted as an open market: on Thanksgiving 2026 a deploy of eight containers was held back whole, with no position open and every entry refused, and had to be forced. The host reads the facts itself (psql through `docker exec postgres`, the monitor's heartbeat, `config.json`, `rules.json`, `docker top admin1` for backtests and studies, the agent's `meta.json` statuses) and fails closed.
  - **Cleaning up** (`Host.cleanup`, `watadeploy prune`, run at each install and from the Disk page): under the apply lock (refused while one runs), the release folders and images `prune` removes, the images no tag names (`docker image prune --force`, dangling only), and Docker's build cache unused for a day (`docker builder prune --force --filter until=24h`). Never `--all`, never a volume.
    - **What prune keeps** is `Host.kept_releases`, each with why (`KEPT_*`): the newest three; one a container is pinned to; one whose compose files made a running container (Traefik, PostgreSQL and RabbitMQ keep 0.59.1's); one the last five applies moved a container from or to, only while that image is there (a rollback recreates on the image with the newest release's files). The status says it (`releases_said`: `installed`, `kept`, `prunable`) at each plan and after each cleanup, and the Disk page offers exactly `prunable` (`releases_to_go`) and says what is kept (`keptSentence`). Until 2026-11-19 the page worked the list out itself, offering 0.59.1 to 0.90.0 while prune removed 0.82.0 alone.
    - **The build cache**: without `--all`, buildkit never prunes a record an image shares, so only the layers no image holds go (those of images removed, the build contexts, node's image, fetched again at the next build); Python and the libraries stay in the images. Two weeks kept 1.5 GB of removed images' layers.
    - **What Docker gave back**: `docker builder prune` is buildx's on the server (Docker 29: the CLI hands `builder` to buildx), whose table ends `Total:\t1.527GB`, not `Total reclaimed space:`; `reclaimed` reads both. Until 2026-11-19 it read neither of buildx's, and the page said "0 B given back"; a figure not said is now said so (`lastCleanupSentence`). Each part said apart, recorded in the status (`cleanup`), which the admin announces once (`cleanup_said`).
    - **The server's own nightly prune**: `/etc/cron.d/docker-image-prune` (no package's, made 2026-04-16) runs `docker image prune -af --filter "until=24h"` at 00:43 UTC; until 2026-11-19 it deleted every WATA image no container ran (the rollback images of 0.84.0–0.88.0, an installed image waiting more than a day for its apply). It now has `--filter "label!=wata.content"` (every image `docker_build.sh` makes carries that label; the old line kept in `/root/docker-image-prune.cron.bak-20261119`). `/etc/cron.d/docker-builder-prune` (Sundays 03:27 UTC, `docker builder prune -f`) is left: it takes what ours takes.
  - **Applying** (`src/release/host.py`): a lock, a dump (`pg_backup.sh now`), then in `ORDER` (backups first, the control service before the admin, the admin last) the guards again, the pin, the recreate, and the admin's `Readiness` criteria read from the host (180 s running and steady, 180 s at work). One that does not stay up goes back to its image of before and the rest waits; one not seen at work stops the rest and stays. `history.jsonl`, `status/status.json`.
  - **From the admin** (System › Release, `src/admin/release.py`, `routers/release.py`; actions enabled, audited): it writes a request into its own `var/lib/admin/deploy/requests/`; `watadeploy-requests.path` (systemd, made by the install) runs `watadeploy serve-requests`, which moves the file out of the admin's reach, reads it without following a link, accepts only the newest release and containers that wait for it (10 min at most), and applies with the same guards. A request may instead be a cleanup (`action: "cleanup"`, nothing else in it but its id, who and when: the Disk page's), carried out as `watadeploy prune` is. The admin never holds Docker, compose or the pins; it reads the status read-only (`/app/var/lib/release`), refuses its own restart plans while an apply runs, announces outcomes once (Telegram, `release` events), and says once after the close what still waits. `watadeploy-config.path` checks, each time `config.json` changes, that every image in use still starts on it (`check_config`, its refusal cleaned as a log line is).
- **Schema** defined as plain dicts in `src/schema/__init__.py` (not pydantic), validated with `jsonschema`.
- **Admin is opt-in** (compose profile `admin`). It reads PostgreSQL through a read-only pool, reaches the other services through what they expose (`/latest-signals`, `/internal/signal`, watchlist endpoints, RabbitMQ) and holds no Docker socket nor Saxo's token folder: it asks the control service for restarts (below). What it writes, through its one writable connection (the pause's): the pause of new entries (`trade_risk_state`), the credentials the operator sets (`credential`, and `credential_check` for the bot it tries), the MCP tokens (`mcp_token`) and a Saxo login's code and state (`saxo_auth_code`); `test_the_admin_writes_five_tables_and_no_other` (`tests/test_admin_vault.py`) holds that list. All its outside access goes through `AdminContext` (`src/admin/context.py`), which tests replace with fakes.
- **Credentials are sealed in PostgreSQL for the services that read them** (`src/vault/`; not `secrets` nor `credentials`, which name the standard module and the admin's sign-in):
  - `credentials.py` lists each (`telegram.bot`, `webhook.token`, `internal.token`, `capital.login`, `heartbeat.url`, `saxo.live.app`, `saxo.simulation.app`, `anthropic.api`), its readers (the roles it is sealed for), its parts (public or secret), how each is checked, where it is laid over the configuration in memory (`overlay`, so that `telegram.bot_token` is read as before) and its old place. A new credential is an entry there, and its readers' tests; a new reader of one needs its row sealed again for it (by a service that reads it already: the admin cannot open what it does not read).
  - `sealed.py` (pure): AES-256-GCM over the value, its key wrapped per reader with X25519 and HKDF-SHA256, the name bound into each (`wata-credential/1/<name>`). `keys.py`: a key pair per role, made by `install_package.sh` (`python -m src.vault keygen`, never replacing one) in `/app/wata/keys`, each private key mounted into its own container alone (`/app/keys/own`), every public one everywhere; held by `tests/test_deploy_compose.py`. Never in `var/lib` (five services mount it whole) nor `etc` (the admin writes it). No dump and no export holds a key, and the research export never the tables.

The scheduler gives up waiting after two minutes and on Docker's stop (`stopped`): CI checks it stops in under 5 s.
  - The admin (`src/admin/vault.py`, `ctx.vault`, routes in `src/admin/routers/credentials.py`) lists them without a value, seals what is entered with the readers' public keys, rotates the tokens (`src/vault/tokens.py`: the one before accepted an hour for TradingView's, 15 min for the internal one) and opens only what it reads itself: the internal token, the Telegram bot, the webhook token on an audited "Show", the Claude API key for its AI agent. Changes need `config_edit_enabled`, are audited with the name and the last four characters only, and apply at the readers' next start (B's restarts; the admin itself opens its two tokens and the Claude API key on demand, `OPENED_ON_DEMAND`).

  - `python -m src.vault migrate` (the compose file's `vault_tools`, profile `tools`, which starts PostgreSQL; `watavault` on the server, made by the install script) moves them in once with the services stopped (`--dry-run` first; only what has no row; the internal token made new) and, later and at the operator's word, `--purge-old` clears the old places, only once the services' own validator takes the purged `config.json` (`refusal_once_purged`: v0.44.0's `ConfigurationManager` still required Saxo's AppKey and AppSecret, and every service would have stopped at its next start). Not in PostgreSQL: what reaches it (its own password, RabbitMQ's), the keys, the control service's token, Traefik's certificates, the admin's sign-in.
- **Saxo's login is in PostgreSQL** (`src/saxo_authen/token_store.py`, `SaxoAuth`'s database path), sealed for the four services that log in to Saxo (`SAXO_READERS`: trader, position monitor, watchlist manager, price recorder):
  - `saxo_token` holds one row per environment (`live`, `simulation`), `generation` written by compare-and-set: a refresh token is used once, and Saxo refuses (and may revoke the grant over) a second use. The lock between containers stays the flock in `var/lib/saxo_auth` (`_token_refresh_lock`): no `SELECT ... FOR UPDATE`, no transaction held across Saxo's answer. A token renewed while PostgreSQL cannot be written waits sealed in `token_spool.json` beside the lock, and the next holder of the lock writes the newer of the two.
  - A lapsed login blocks nothing: `needs_authorization_since` is set once (Telegram said once, `REMINDER_EVERY_SECONDS` after), the lock released, a code looked for every 5 s for 5 min, then `AuthorizationRequired`. A code is in `saxo_auth_code`, sealed, claimed by one `UPDATE ... RETURNING` (only one service exchanges it), fresh for `CODE_FRESH_SECONDS`.
  - Saxo's addresses are constants per environment (`src/saxo_authen/endpoints.py`), the redirect the server's (`SAXO_REDIRECT_URL`, `.env`): every container connects to PostgreSQL as the same user, so a row is no proof of who wrote it, and an address read from one could send the next code elsewhere. The apps keep their AppKey and AppSecret alone. A service reads the token file of before while it exists (`_chosen_store`) and config.json's app while its row is absent.
  - The admin (`src/admin/saxo.py`, `ctx.saxo`) reads the row's dates, never a token; `authorize` makes a link with a random `state` kept hashed 10 min, used once by the callback (`/api/saxo/callback`, public: the state admits it, `src/admin/routers/saxo.py`) or by the address pasted; `hand_over` seals the code. `watasaxoauth` (`src/saxo_authen/cli.py`) does the same on the server.
  - `saxo_auth.env` stays a setting of the server: a switch would mix the two accounts' positions in `turbo_data_position`, whose reconciliation would close the other's rows.
  - `python -m src.vault migrate` moves the token file in under the flock and renames it `.imported` (a container of before must never use a refresh token renewed since); `export-saxo`, in the trader's container (`vault_tools` holds no private key), writes it back for a return to v0.43, encrypted with the secret of the app the services log in with.
- **The MCP tokens are in PostgreSQL** (`mcp_token`, `src/admin/mcp_token_store.py`, outside `src/admin/mcp_server`, which still imports no `src.database`): their sha256, read again every 5 s for the gate (`keep_fresh`), a last use written once a minute at most; made from the System page (shown once) or `watamcptoken`. The file of before is moved in the first time the table is empty, then renamed `.imported`.

What a service does not run with (`pending_changes`) comes from the editor's journal of saves against the container's start, a hand edit said from the file's time. Restarts are never the MCP endpoint's (`tests/test_mcp_boundary.py`).

- **What the trading services do for the admin** (all additive, none may block or fail a trade): the trader checks `TradingRule.check_entries_paused()` before opening and journals each signal's outcome in the background (`SignalJournal`, table `signal_journal`); the position monitor publishes `AsyncPerformanceMonitor.live_values()` to `position_live_value` on a timer and handles the `close_position` ops message (ignored when older than 60 s); both record the account balance with the daily report (`account_balance_history`) and keep what became of each order they send (`OrderTracker`, table `order_execution`).

- **Price recorder is opt-in** (compose profile `recorder` + `trade.config.price_recorder.enabled`) and outside the trading path: it reuses `AsyncInstrumentService.build_watchlist_candidates` and `SaxoStreamClient` unchanged, validates its own config section (`src/price_recorder/settings.py`, deliberately not in `ConfigurationManager`: a mistake there must not stop the trader), and creates its own tables (`PRICE_HISTORY_SCHEMA_SQL`, not part of `init_schema`). `BarBuilder` (`bars.py`) is pure and time-driven; the stream callback must stay memory-only. Lost bars cannot be re-fetched from Saxo, so a change that can drop them needs a test. Untested against Saxo.
- **What Saxo answers of the turbos, asked without trading** (`src/price_recorder/tradable_probe.py`, `wataprices tradable`, in a container of the recorder's on the newest image; since v0.91.0): the session's level, the gateway's round trip and HTTP version, each turbo's details (the order types and durations Saxo takes on it: `ImmediateOrCancel`, `FillOrKill`, `Switch`...), and for `--minutes` its InfoPrice (asked as the watchlist manager asks it) beside its tradable price (`/trade/v1/prices`, which WATA reads nowhere else), streamed on a WebSocket and context of its own: changes and the seconds between them, how far apart the two asks stand, and the shift that brings them closest (`lead`). By default the two turbos of each direction the trader would buy first. Every request goes through `GuardedClient`: outside `ALLOWED` (never `/trade/v2/orders` nor a change of the session) it is refused before it leaves (`tests/test_tradable_probe.py`). Its subscriptions are removed one by one at the end, a run cut short included. It decides whether WATA could size and judge on the tradable price, and send orders that never wait at Saxo: the measures of 2026-11-18 (`data_execution`) found Saxo answering an order in 0.26 s and filling it within 0.05 s of that, two market sales kept working 31 and 58 s, and entries paid 0.59 % (median) above the InfoPrice ask they were sized on. Untested against Saxo.
- **The recorded bars are keyed by instrument and time, in monthly partitions written in time order** (`price_bar_10s`, 162 bytes a bar with its key on the server, about 185k bars a trading day in October 2026). A read of one instrument goes through the key; a read of a period across instruments (the research export's day, Availability, `wataprices export`, the lab's reload of a day) goes through the BRIN index on `ts` (`idx_price_bar_10s_ts`, 32 kB a month), which the recorder builds at its start: 0.5 s for a month of 4.8 million bars, under the pool's 30 s `command_timeout` (a start that fails exits, and its bars are lost). A turbo's day is spread over every page of that day, so it reads as many pages as all the turbos' day: rewriting a closed month in key order (`CLUSTER`, 15 s of exclusive lock for a month on a Mac) cuts that about 30 times, but leaves the BRIN index nothing to skip in that month. Measured on pgserver over a month made up in the server's shape, and on the server before the index (2026-10-25, read-only): a day across instruments read all 25,598 pages of October (177 ms), one turbo's day 2,966.
- **Backtests trade the recorded turbos as WATA would have** (`src/backtest/`, outside the trading path: no trading service imports it). The signals are a Pine script's alerts, run as the TA engine runs a signal rule, those WATA received (`signal_journal`), or those a rule raised as the engine journaled them (`ta_signal`, source `ta_signals`: no script run again; read by `ask_backtest` through `AdminQueries.rule_signals`, the newest `MAX_RAISED_SIGNALS` (20,000) of the period, refused past it). A simulated trader and position monitor buy and sell the turbos the price recorder kept, at their recorded ask and bid. An entry with no turbo recorded at that moment is not traded (`unpriced`), so a run covers only the days the recorder ran.
- **The backtest repeats WATA's rules** (`src/backtest/rules.py`, `simulator.py`): the trader's checks on an entry, in `handle_trading_signal`'s order (an entry refused buys nothing, and with `close_on_refused_entry` still sells the positions held the other way when the signal itself stands, above; with a cash reserve, an entry that failed still sells the other side, `_sell_after_failed_entry`); the orchestrator's sizing (`_calculate_position_scale`, `_calculate_bid_amount`); the position monitor's exits (`AsyncPerformanceMonitor._evaluate_positions`, with its reason strings, which `src/admin/analysis.py` groups as the Exits page does; the sale before a release, `news_flatten_minutes_before`); the scheduler's close of the day; the window around US releases (`news_*` settings read from the `macro_news` rule, the calendar handed to `entry_refusal`). The turbo is chosen by the live helpers themselves (`select_turbo` in `selection.py`). `tests/test_backtest_parity.py` runs the live code on the same inputs: a change to one of those must be made in the mirror too, or backtests describe a WATA that no longer exists.
- **A turbo's price at a moment is the open of the ten-second bar that starts at or after it** (`ceil10`, `TurboSeries.quote_at` in `src/backtest/data.py`). `BarBuilder` makes a bar for every bucket while the feed is alive, so the price is at most ten seconds late and never early. No bar while the recorder listened (`price_recorder_coverage.feed_ok`) means not quoted (below for what a backtest then does). Inside a bar the monitor sees open, low, high, close (high before low when it closed lower), `RangeBarBuilder`'s order; how a stop crossed inside ten seconds fills is a setting (`stop_fill`). The trader is sequential: a signal is decided once the orders of the one before are filled, and those that came meanwhile go through the web server's store first (`stored`, held to `SignalStore` by a test): only the newest of each indice, a close never replacing an entry of the same moment, the others journaled `superseded` or ignored.
- **An order is priced at the turbo's next quote** (`fill_price`: `next` for a new run, set by `from_config`; `standing`, the quote at the fill as above, for the runs made before, the default of `from_dict`): the bid and ask at the end of the first bar from the fill in which Saxo sent a new quote, within `NEXT_QUOTE_SECONDS` (120), else the standing one (`TurboSeries.next_quote`; a change is read from the bar's prices, `changed_inside`, which agree with the recorder's count of updates in 99.8 % of bars). Of WATA's 31 purchases of 13-20 Oct 2026, the standing ask was 0.48 % under the price paid on average (8.3 % on 19 Oct), the next one 0.04 %. A sale by a signal, the day's close or before a release likewise; an exit of the monitor sells at the bid that decided it (a stop crossed inside ten seconds as `stop_fill` says), less `exit_slippage_percent` (0.1 % for a new run, as WATA's real exits sold; 0 for the runs made before; fixed fills only). Measured fills are priced at the same quote, plus what WATA's orders paid beyond it, drawn (below); those of the runs made before v0.100.0, and of a run priced at the standing quote, keep the quote when the order left plus a slippage measured against that one (`Simulator._next_quote`, `fills.at_fill`). The simulator judges a position as the monitor does (`wait_for_fresh_quote`, from the live configuration; off for the runs made before), parity tested: with `next` and the wait off, a run replays the monitor of before, its false exits included. A fill 1 % or more from the standing quote is said in the trade's notes. An order that costs more than the account holds at the price paid is refused, as Saxo refuses it (`funds_refused`, `[InsufficientFunds]`): it is sized on the standing ask with one turbo of margin, 0.5 % of 1,000 € at 5 €, and 13 of the 37 entries of a run of 7 Nov 2026 cost more. It is then sent again with fewer turbos as the live trader sends it (below), each attempt filled an order's time after the refusal at its own next quote: the signal and the trade keep the orders refused (`refused_for_funds`), the trade's note says so, the summary counts them (`rests_on.funds_retried`); the runs made before send nothing again (`funds_retries` 0, the default of `from_dict`). A quote Saxo says is delayed is not bought (`delayed_minutes`, read from the recorder; `no_market_reason`).
- **When Saxo does not quote a turbo, a backtest does what live does** (`src/backtest/simulator.py`; `tests/test_backtest_gaps.py` builds its days through the recorder's own `BarBuilder`). The data holds two outages: a hole (Saxo flags the turbo: no bar) and a frozen quote (Saxo sends nothing while the stream lives: the recorder writes the last quote again every 10 s, `updates` 0).
  - A sale that finds no quote waits for one (`pending_sale`), tried again at the moments of `retry_after` (`src/trade/close_intents.py`, in `_CODE`) and filled at Saxo's first new quote (`_requote`): never at the open of the first bar after a silence of the stream, which is the quote of before. Its cash comes in only then.
  - Held through a hole, a position is judged on the index as `judge_between_quotes` judges it (`_judged_during_hole`, with `index_between_quotes`, within `QUOTE_FRESH_SECONDS`), and sold before a release whose window began inside it (`_flat_window_between`).
  - Never quoted again that day, it is carried to the same instrument's next recorded day (`_carry_over`, flag `carried`); at the run's end, closed at its last bid and said unresolved (`Simulator.finish`, which `run.py` calls once the days are done, for the random entries too).
  - Knocked out, at 0 and without costs, where the run's index (`index_epic`, loaded whenever the configuration names one) reaches the turbo's level after its last quote (`IndexSeries.crossing`); without the index only, by its bid under a quarter of the day's high (`knock_out_guess`), which missed 2 of the 3 real knock-outs of 5 Nov 2026.
  - An order filled on a quote unchanged for `FROZEN_QUOTE_SECONDS` (120) while the index moved a tick is priced from the index (`_unfrozen`: `TurboSensitivity` fed with the day's quote changes; with fixed fills only, a note with measured ones).
  - Each trade carries what it rested on (`flags`, `FLAGS`), counted in the summary's `rests_on` (`figures.rests_on`) with the entries refused for funds and the days recorded for less than `PARTIAL_SHARE` (95 %) of their trading hours (a day's `partial` and `recorded.share`).
- **A run or a study that dies says how and where** (`failure_of`, `failure_sentence` in `src/admin/backtests.py`, `StudyService._ending`): the exit's meaning (`exit_said` in `src/price_history/process.py`: −9 the kernel, −6 Node's full heap), the phase and day from `progress.json`, the engine day the runner was given with its bars and the runner's peak memory (`Progress.runner_day`, from `ReplaySession`'s `on_window`), the container's memory then and the kernel's OOM kills during the run (`memory.events`); in its status as `failure` and its error. The runner says its last stderr lines when it ends (`NodeRunner._last_words`), and the replay the engine day it was on.
- **Backtests asked for from the admin are child processes and folders of files** (`src/admin/backtests.py`, reached as `AdminContext.backtests`):

It writes under `admin.persistant.backtests_path/runs/<RUN_ID>/`, `summary.json` last.
  - A run id is made by the service and matched against `RUN_ID` before any path is built: keep it that way for every new route.
  - For a replay of the journal, the route reads it (`AdminQueries.journal_between`) and WATA's closed positions of the same days (`closed_positions`), and the service hands both to the child as files.
  - They change nothing live, so they are not operator actions (no audit entry, no Telegram but a configuration's nightly line the operator asked for, below), and have their own switch (`admin.backtests_enabled`). 365 days (731 on made-up turbos; 92 until v0.94.0), 10 waiting and 3 h at most, one at a time: `admin.backtests_workers`, `backtests_max_queued` and `backtests_max_period_days` say otherwise, which the lab does (4, 500, 731). A full line is `LineFull` (a `NotPossible`), which a nightly run waits on.

- **A run made with older code is made again when the operator asks** (since v0.74.0; `BacktestService.remake`, routes `GET|POST|DELETE /api/backtests/remake`, the list's "Make them again" and a run page's "Make it again"):
  - A remake is the same run on today's code: its request (name, tags, experiment and maker kept), its `settings.json`, sources, journal, raised signals, positions, turbo model and measured fills copied as a stress copies them (`_queue_run(..., copy_from=)`), plus `remade_from`. It adds no trial to the experiment journal (trials are its `record_run` events). Paper runs are left to paper trading (`_remake_stale`).
  - The runs to make again are kept in `remakes.json` beside the runs, and given to the line in `_next` one at a time, only when nothing else waits: never in the way of a run asked for, and the queue's places stay free. A stress or a model check waits for the run it judges when that one is made again in the same batch, and is then made of the new one (`stress_of`, `model_check_of`, a model check's recorded trades the new run's). "Stop" drops what waits; one cut by the admin's stop is asked again at its next start (`_recover_remakes`).
  - Once done (`_settle_remake`), the old run gets `remade.json` (`remade_by`) and stays, folded under the new one in the list (`collapseAttempts`), and a rule's reference and the live reference that named it name the new one (`paper/references.json`). One that fails leaves the old run as it was, its failure folded under it.
  - The route chooses the runs in a thread (`remake_candidates`) and adds them on the event loop (`add_remakes`), where the line changes the same file.
  - A configuration's nightly run is not offered while its configuration's nightly is on (`_why_not_remade`, `remakable` of `model.ts`): the next evening makes it again on today's code. A remake drops the nightly mark. A run made from another (a stress, a model check, a cell) never takes `remade_from` nor `nightly` (`_derived`, `DERIVED_DROPS`): until v0.94.0 one made from a remade run settled as a remake once done, wrote the original's `remade.json` and took its references.
- **Backtest configurations, and their nightly re-run** (since v0.94.0; `src/admin/backtest_configurations.py`, pure but its store; `src/admin/backtest_nightly.py`, `ctx.nightly`, a task of the admin's lifespan while backtests are on; routes `GET /api/backtests/configurations`, `GET|PATCH /api/backtests/configurations/{id}`, `POST …/{id}/extend`; outside `_CODE`: no run turns stale):
  - **A configuration** is every run whose result is decided by the same things but its days: `configuration_id`, 12 hex of the sha256 of canonical JSON (sorted keys, every number a float so that `2` and `2.0` are one, bools kept) of `strategy_parts` (kind, indice, turbos, chart, the source's defining parts: a Pine run's script id/version/sha256, libraries, asset, side, bars, inputs `id → value`, alerts `title → action`, `alert_calls`, `confidence_plot`; a rule's id; a sweep's axes, held-out share and walk-forward) and of the settings as resolved (`BacktestSettings.from_dict(settings.json).to_dict()`), each setting still at its `BacktestSettings()` default left out, so that a setting added later re-keys nothing. Left out: the period, name, tags, favourite, random entries, who asked and why, the lock box, `remade_from`, `from_rule`, the source's counts, the turbo model and measured fills. Capital counts (the operator's choice): the four "(again)" runs of 16-19 Nov 2026 are two configurations, 1,000 € and 100 € (pinned in `tests/test_admin_backtest_configurations.py`). Runs of one `strategy_id` with other settings are "same strategy, other settings" (`related`, `distinct`). A stress, a fill-noise one, a model check or a forward check's run belongs to its base's configuration while the base is there (`BASE_KEYS`); a paper run to none. `BacktestService.identity` caches what decides it per run (never what could not be read); `_described` gives each run its `configuration` and `nightly` (`{configuration, on}`), and so does MCP `backtest_list`.
  - **What is kept beside the runs** (`ConfigurationStore`, `<backtests_path>/configurations/`): `index.json` (the operator's name, `nightly` `{on, from, since, telegram}`, its `last` ask `{day, run, asked_at, error, settled, by_hand}`, `seed_run` and `digest_version` to key it again should the digest change) and `<id>.json`, what each nightly run said, newest first, 400 lines. One `threading.Lock`, ids matched before any path; a run's state is always read from its `status.json` (`recover()` rewrites it), never stored. An entry whose runs and first run are all gone is forgotten (`_forget_gone`), never while no run can be read.
  - **The nightly run**: once the market is closed by the live rules, for each configuration switched on whose finished runs do not cover tonight's window, one at a time, only while no run of the operator waits (`operator_waiting`) and the oldest asked first (`due`, `catch_up`, a 300 s tick, woken by the finish hook). The window is `nightly_window`: from the anchor chosen (`from`) to `debriefed_day` (moved into `paper.py`: today once its trading hours are over), at most min(365, the runs' period limit) days, then its first day moves on. The run is `BacktestService.extend`: the newest finished run of one combination made by itself, its request, `settings.json`, sources, turbo model and measured fills as they were (`copy_data=False`: the template's positions and raised signals are of its own days), its period and name changed, `nightly: {configuration}` set; the journal's signals and positions, or a rule's (`newest_raised`, shared with paper reports), read again for the new days. One refused (no entry signal, a period too long) is kept as such in `last` and not asked again that day; a failed or stopped one waits for the next day; one the admin cut (interrupted) is asked again. "Bring it up to date" (`bring_up_to_date`) asks it at any hour, room checked.
  - **Settled** (`settle`, from the service's finish hooks, `BacktestService.on_finished`, each in try/except so that a hook's error never turns a DONE run into FAILED, and again at each tick, idempotent on `last.settled`): done, its line goes into the history and the configuration's older nightly runs are removed unless something rests on them (`_kept`: a favourite, a run named by `references.json`, the base of a stress, a fill-noise one or a model check, a run the AI agent gave a verdict on, read from its `verdicts.json`); runs made by hand never; references never moved, Edge Watch judging from its reference's own last day. With `telegram`, one line through `ctx.notifier` (`said_line`), a failure said too, never raising. `GET /api/backtests/{run_id}` of a nightly run replaced answers 404 with `replaced` (`ConfigurationStore.replaced`), which the run page turns into a way to its configuration.
  - The runner's answers read lately are pruned last (`_cache_files` takes `max(st_mtime, st_atime)`): a nightly run reads the same days' answers each evening, which a cache hit never rewrites (`src/ta_engine/replay.py`, in `_CODE`).
- **Forward checks: did a kept conclusion hold?** (since v0.95.0; `src/admin/forward_checks.py`, `ctx.forward`, a task of the admin's lifespan while backtests are on; routes `GET|POST /api/research/forward`, `GET /api/research/forward/{id}`, `POST …/{id}/stop`; outside `_CODE`: no run turns stale):
  - **Started** by `exp_conclude(verdict="kept", candidate=<run>)` (MCP and the AI agent: `ForwardReads` of the facade, never the service, which speaks on Telegram), or by the operator for an older conclusion (the Experiments page's form). Refused in words (`NotPossible`, the conclusion kept all the same): `MAX_ACTIVE` (10) run already, the experiment has one, the candidate is not one of its finished runs of one combination (`candidate_refusal`, `_belongs`), its Edge Watch model cannot be drawn from (`ew.build_model` unchanged, kept in `_research/forward/models/`: Edge Watch's `_prune` would delete it from its own folder), or it makes no more than random entries.

A run made from another (`forward_of` in `BASE_KEYS` and nightly's `DERIVED`): never a nightly template nor a covering run, never judged (`isJudged`, `run_verdict.is_judged`), never made again (`_why_not_remade`), and `_derived` drops `forward`/`forward_of`. - **A range is counted in the asset's own tick**: R60 is 6 points on Capital.com's US100 (a tick of 0.1), 0.06 on Dukascopy's (0.001: its files hold thousandths, and 6 points are R6000). - **A backtest is never read alone** (`src/backtest/baseline.py`, `figures.py`). - **A sweep** (`src/backtest/sweep.py`): two axes and 64 combinations at most, an axis being a setting or a script input. - **A run's results are read beyond its total** (`src/backtest/robustness.py`, pure): risk figures on the daily results in `figures.risk` (Sharpe, Sortino and Calmar brought to a year only from 20 days, `ANNUALISED_FROM_DAYS`; time under water; the worst 5 % of days; payoff; the share of its best a winning trade kept), and in `summary.stress` the drawdown of the same days drawn again (seeded) and the total without the best days. A sweep keeps each combination's daily `curve`; its summary adds a walk-forward when asked (`sweep.walk_forward`: the best of the days before chosen again window after window, judged on the days after), the probability of overfitting (combinatorially symmetric cross-validation, from 8 days) and the deflated Sharpe ratio (from 20 days to choose on), with the trials made before counted (`sweep.trials_before`, which the lab passes from its journal). `tests/test_backtest_robustness.py` checks the deflated ratio against Bailey and López de Prado's own example.
- **A stress sweep is the run made again with worse fills** (`BacktestService.stress`, `POST /api/backtests/{id}/stress`): order time × slippage around the run's own (`STRESS_LATER_SECONDS`, `STRESS_WORSE_PRICE`), its own fills the first cell, `stress_of` in its request. It chooses nothing, so its summary has no overfitting figures. A fill-noise stress (`kind=noise`, MCP `backtest_derive` kind `noise_stress`) moves each fill at random by up to `NOISE_PERCENT` either way (`fill_noise_percent`, drawn by `fill_noise_seed` and the day), four draws each, `noise_of` in its request and its spread in `summary.noise` (`figures.noise_spread`): not the stress the verdict reads. A combination of either made a run is an ordinary run (`run_cell` drops both).
- **The edge of the entries** (`src/backtest/edge.py`, `edge.json`, a headline in the summary): how the chart's asset moved 1 to 60 minutes after each entry signal, taken or not, signed by its direction, beside random moments of the same hour of the same day (seeded). The t-statistic is every signal's mean over its spread, only the signals whose windows do not overlap counted as observations. A run's, not a sweep's. The pages read it without its signals one by one (`BacktestService.edge`); the lab reads the file.
- **What kind of day each day was** (`src/backtest/regimes.py`, `days.json` `regime`): gap, range, realised volatility, trend or back and forth, the US open's first half hour, in the rules' trading hours of the chart's asset; groups in `labels` (volatility in thirds of the run's days). Each trade gets `session_part` and `minutes_after_open` (9:30 in New York, whichever city changed its clocks). The macro news come from `src/trade/data/macro_calendar.csv` (read by `src/trade/macro_calendar.py`, which the trader shares): each row names the official page it was read from (the Fed, BLS, BEA, Census), the releases the 2025 shutdown cancelled are absent and the delayed ones at their day. A day is known by FOMC, CPI, NFP and PCE alone (`DEFAULT_EVENTS`, `MACRO_LABELS`): the kinds kept from late 2026 would split a run's days in two. It is not code: a run notes its digest and the day it ends (`made_with.calendar`) and warns past it. Keep it ahead: `python -m lab calendar check`.
- **Turbos made up from an index, for long histories** (`src/backtest/turbo_model.py`). Measured on the recorded turbos against Dukascopy's `us100` (`calibrate`, a child process of the admin from the Backtests page, kept under `backtests_path/_turbo_model/`): by direction, euros of turbo per index point and the level a turbo's price would be nothing at against its knock-out level; the spacing of the levels, the spread by hour, the hours turbos are quoted. `ModelData` makes each day a ladder of levels around the open, priced from the index and knocked out where it crosses one, with the interface of `DatabaseData`: the selection, the simulator and the pages are unchanged. A run on them (`turbos: "modelled"`) copies the measure into its folder (`turbo_model.json`) and says so (`made_with.turbos`); the euro's rate is held at what it was measured at. A model until checked on the recorded days: a model check (`BacktestService.model_check`, `POST /api/backtests/{id}/model-check`, MCP `backtest_derive` kind `model_check`, the run page's "Check the turbo model") makes a finished run of the recorded turbos again on made-up ones, without random entries; its folder keeps the recorded run's trades (`recorded_trades.json`) and the child pairs them with its own by signal (`compare_trades`, `model_check.json`, the summary's `model_check`). The lab's `python -m lab model validate` does the same from a spec.
- **What each real trade lost between its signal and its fills: the execution ledger** (`src/admin/execution_ledger.py`, `GET /api/execution`, the Orders page's "What execution cost", MCP `data_execution` parts `ledger` and `trades`; since v0.85.0). Per closed position, from what the services recorded (`turbo_data_position`, `order_execution`, `order_request`, `signal_journal`, `signal_alert_time`, `ta_signal`) and the turbo's recorded quotes (`price_bar_10s`, the execution calibration's `QUOTES_SQL`): the signal's way to WATA (from TradingView's alert, `signal_alert_time`, its `signal_timestamp` being the bar's open; from the engine's bar close), WATA's decision, Saxo's acceptance and fill (two clocks), a sale's attempts; and its costs in points of its result, a cost positive: the delay (the recorded ask when the purchase left against when the signal was raised), the entry slippage (paid above the ask the order was sized on, `order_request.price_seen`), the exit slippage (the price the sale was decided on, Saxo's bid or the index's estimate read from its reason, above the price sold at, over the price paid), the spread apart (already in the result). In all, by exit, by what an exit was decided on and by source. An absent table reads as no rows (`_fetch_optional`): the ledger lists the trades all the same. Outside `src/backtest/` and `src/trade/`: nothing of it is in a backtest's code digest (tested).

- **What WATA's own orders took and cost** (`src/backtest/execution_calibration.py`, `GET /api/backtests/execution`): from a signal to the trader's decision (for a signal that bought, its order leaving: `decided_at` is written after the trade), from an order to Saxo's acceptance (over `ORDER_SECONDS_MOST`, 30 s, left out and counted: the waits before v0.48.0), the refusals by hour, and the price paid, measured twice. One SQL for the admin and the lab (`read_rows`); the form offers the measured values for a run.

Saxo sends a turbo a new quote about every 30 s and fills at its live price, so this is mostly the turbo's move since its last quote (0.48 % of 31 purchases of 13-20 Oct 2026, 9 % on a quote 60 s old, 2.74 % on the first live entry of 23 Nov): no cost, the position is worth what was paid.
  - **Against the quote a run prices the order at** (`slippage_at_fill`, since v0.100.0; `at_the_fill`, read by the run's own `TurboSeries.quote_at` and `next_quote` on the turbo's bars around the fill, `BARS_SQL`, the fill being Saxo's acceptance): for an exit of the position monitor that left on a quote Saxo had just sent (`quoted_just_before`: a new quote in the ten seconds its order left in, or the ten before; never a sale the trader sent, `explicit`: its close reason says "Explicit Close"), the bid standing when its order left, which decided it (`slippage_exit`, in percent of it too); the next quote from the fill for a purchase (`slippage_buy_next`) and for any other sale (`slippage_sell_next`: the trader's, the monitor's by the clock, and the stop of 19 Oct 2026, "hit" on a bid older than its purchase and sold 9 % above it, which set against that bid would be drawn as a windfall no exit gets). What a run has left to add: `suggested.slippage` is the median of the first two together, `suggested.exit_slippage_percent` that of the third, each from 10 measures (`LEAST_MEASURES`). Until v0.100.0 `suggested.slippage` came from the first measure (0.02 € in November 2026), which a run priced at the next quote counted a second time.

A stress cell's later and dearer steps add to the draws. `made_with.execution.priced_at` says `fill`.

Drawn at random for another order, the turbo's move since its last quote became a cost that order never had, each side on its own (the purchase of 19 Oct paid 9 % above a stale ask and was sold 9 % above a stale bid: +0.5 %; drawn apart, two losses of 9 %), and its largest a stop-loss at the position's first quote. A new bar of a continued run was under a millisecond before and after: this is for backtests (each engine day is a whole run), the engine's loads and checks, and a rule that fell back to whole runs.

What the script computes is untouched. The answer holds the alerts read and, when a plot is read, every plot at those alerts' bars alone.

It says more than the plots did: every variable the script has, where a plot showed a few. Seen to agree over 3,000 appended bars of the live script, and to catch a value changed by hand (`runnerCore.test.ts`).

Five jobs: `tests.sh` on each Python of the matrix; the image built for each, with the Pine runner built into it first, `python -m src.release.check` run inside it (what the install checks: every service loads, the libraries, the validators, the runner confined) and the manifest read inside it as the server reads it; the images built by the server's own `docker_build.sh`, with a toy compose project on real Docker where one pinned container is recreated alone and the other untouched; the live tests against PostgreSQL and RabbitMQ; the admin interface. `tests/test_deploy_compose.py` keeps the workflow, the `Dockerfile` and the compose file saying the same thing (the Python of the image is in the matrix, the live tests get the compose file's images)
- **Build package**: `./package.sh` → creates `wata_app_v<VERSION>.zip`
- **Deploy**: `./deploy_app_to_your_server.sh` from `deploy/tools` (Ansible playbook `deploy_app.yml`): installs the release beside what runs (nothing stops), says the plan, then applies what may go now (`watadeploy apply`); what is held back waits for `watadeploy apply` or the System page. `-e apply=none` installs only, `-e services=...` applies those, `-e force=true` whatever holds them back, `-e full=true` stops and starts everything (infrastructure changes)
