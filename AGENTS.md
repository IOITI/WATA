# WATA — AGENTS.md

## Project

Automated trading assistant for Saxo Bank Knock-out warrants (Turbos). Python 3.14, FastAPI, async microservices in Docker.

## Service map

| Role               | Entrypoint (`__init__.py`) | Communicates via                          |
|--------------------|-----------------------------|-------------------------------------------|
| `web_server`       | `src/web_server/`           | FastAPI on `:80`, query-param token auth  |
| `trader`           | `src/trader/`               | HTTP-polls web_server `/latest-signals`; hands what it could not sell to `trading-ops` |
| `position_monitor` | `src/position_monitor/`     | Saxo WebSocket streaming + `trading-ops`  |
| `scheduler`        | `src/scheduler/`            | Publishes to `trading-ops` / web_server   |
| `telegram`         | `src/mq_telegram/`          | Consumes `telegram` queue; answers the bot's read-only commands (`reporting.telegram_commands`) |
| `watchlist_manager`| `src/watchlist_manager/`    | REST API on `:8081`                       |
| `admin`            | `src/admin/`                | FastAPI on `:8082`, cookie session; serves the React UI built from `admin_ui/`; its AI agent calls the Claude API |
| `price_recorder`   | `src/price_recorder/`       | Own Saxo stream; writes PostgreSQL only. Nothing calls it |
| `capital_feed`     | `src/capital_feed/`         | Own Capital.com stream; writes PostgreSQL, publishes live prices to RabbitMQ `wata.prices`. Nothing calls it |
| `ta_engine`        | `src/ta_engine/`            | Reads the Capital.com feed's tables; runs the signal rules' Pine scripts in a confined Node child; POSTs live rules' signals to web_server `/internal/signal` (Bearer). Nothing calls it |
| `service_control`  | `src/service_control/`      | FastAPI on `:8090` of `control-net`, which only the admin joins (Bearer, a compose secret); holds Docker's socket to restart WATA's own containers |

Each service runs as a Docker container; `WATA_APP_ROLE` env var selects which `__init__.py` runs via `src/start_python_script.sh`.

## Infrastructure

- **RabbitMQ** — queues: `trading-signals` (trade actions, no longer consumed), `trading-ops` (ops/daily_stats, and the closes the admin asks and the trader hands over), `telegram_channel` (notifications); topic exchange `wata.prices` (the Capital.com feed's live quotes and bars, transient, read by the admin while a chart follows them)
- **PostgreSQL 16** — replaces DuckDB (migrated in v0.7.0). DuckDB config is dead. Dumped by `pg_backup1` (`deploy/pg_backup.sh`): each night at 02:17 UTC without the bars' rows, whole on Sundays, 14 and 4 kept in `var/lib/backups` (`last.json` for the admin's health, read-only), pulled to the Mac by `lab/sync.sh`; `docker exec pg_backup1 sh /pg_backup.sh check` restores the newest into a scratch database and counts the trading tables. With `BACKUP_AGE_RECIPIENT` and `BACKUP_S3_BUCKET` in `.env`, each dump is also encrypted with age to the operator's public key (its private half stays on the Mac) and sent with rclone to an S3-compatible bucket, 14 nightly and 8 Sunday copies kept there (`last.json`'s `offsite`; health warns after two nights without a copy sent); the image is `wata-backup:<version>` (`deploy/pg_backup.Dockerfile`, age and rclone pinned by version and sha256, and the script copied in, built by `docker_build.sh` from those two files alone; its build arguments are `PINNED_*`, since rclone takes any `RCLONE_<flag>` of its environment for that flag, and `RCLONE_VERSION` was read as `--version`), and nothing on the server can decrypt. `python -m lab backup check [--offsite]` restores the newest dump, or the bucket's newest copy, on the Mac and counts the same tables. Out of memory, the kernel kills the admin and the backups before the trading path (`oom_score_adj`, `tests/test_deploy_compose.py`). Its container has 1536M, `shared_buffers` 512MB, `effective_cache_size` 1GB, `work_mem` 16MB and a `/dev/shm` of 256m (`command` and `shm_size` in the compose file, held by `tests/test_deploy_compose.py`), for a server of 8 GB: a change of them restarts the database, so it waits for a closed market.
- **Traefik** — reverse proxy, Let's Encrypt, TradingView IP allowlist
- **Config** — JSON at `WATA_CONFIG_PATH` path, validated strictly by `ConfigurationManager`

## Testing quirks

- **`WATA_CONFIG_PATH` must be set** before importing `src.web_server` (tests set `os.environ["WATA_CONFIG_PATH"] = "tests/test_config.json"`)
- Test config at `tests/test_config.json` — omit `day_trading` rule if testing with `trading_mode != "day_trading"`
- `tests/test_web_server.py` patches `verify_token` and `Request.client` for IP filtering tests
- `tests/test_config.json` uses minimal rule set; adding more rules requires updating config
- Some tests run the real Pine runner and need Node 22+ on the PATH (Node 24 through nvm) and `runner.mjs` built; they are skipped otherwise
- The tests replace PostgreSQL with fakes that only record the SQL text. New SQL can be run for real without Docker: `pip install pgserver asyncpg` in a throwaway virtual environment gives a PostgreSQL 16 in a folder (`pgserver.get_server(path).get_uri()`), which `PostgresConnectionManager`, `init_schema` and the managers accept as they are
- **`tests/test_infrastructure_live.py` is the database and the queue for real**, through the services' own code. It is skipped unless given `WATA_TEST_POSTGRES_DSN` and `WATA_TEST_RABBITMQ` (`user:password@host`), and must be run on its own: in a run of all the tests, other files have already put an empty module in the place of `asyncpg` and `aio_pika`. CI runs it against a PostgreSQL and a RabbitMQ of its own. Only for ones that can be thrown away: its messages go to the queues the services read
- **The stream client's connection is tested against a WebSocket server on the machine** (`LocalSaxoStream` in `tests/test_saxo_streaming_client.py`): opening, reading, Saxo dropping the connection, coming back with the last message read, leaving. Those tests are what says whether an upgrade of `websockets` keeps the position monitor's link to Saxo working: run them before and after one

## Architecture notes

- **Trader does NOT consume RabbitMQ** for trade signals — it long-polls `web_server:80/latest-signals` via `SignalPollingClient`. Old RabbitMQ `trading-signals` queue consumption was removed.
- **Signals are executed once.** The web_server store keeps the latest signal per indice until a newer one replaces it, so the trader dedups on `signal_uuid` (`select_signals_to_dispatch` in `src/trader/__init__.py`).
- **No entry around US releases** (the optional `macro_news` rule of `trade.rules`, off unless it is there): from `minutes_before` a release to `minutes_after` it (`minutes_after_fomc` for an FOMC statement, whose press conference follows), for the releases its `events` name (FOMC, CPI, NFP and PCE unless it names others, `DEFAULT_EVENTS`; PPI, RETAIL, GDP and JOLTS, kept from late 2026, only once named); with `flatten_minutes_before` (0 unless given) the position monitor also sells what is held from then (see below). The calendar is `src/trade/data/macro_calendar.csv`, read by `src/trade/macro_calendar.py` (`NewsRule`, `window_at`, `refusal_text`): the trader reads it, so it lives on the trading side, and the backtests import it from there (never the other way). New York's hours, whatever either side's clocks. `TradingRule.check_macro_news` runs right after `check_market_hours`; an unreadable calendar never stops the trader. Past the calendar's last known day of the releases the rule names nothing is known and entries go on; from 30 days before it, the scheduler says so on Telegram each morning and the admin's health has a warning (`upkeep`, which names the kind that ends first). Each kind is known from its first row (`Calendar.since`, `known_from`): a backtest that names a kind on days before it says so. ISM's manufacturing index is not kept: only its rule is public, its dated calendar is for ISM's members. `ConfigurationManager` checks the rule only when it is there.
- **One moment, one trade: an entry wins over a close of the same moment.** An entry sells the other side before it buys, and a close taken after it would sell the position just opened. The TA engine and the replays (backtests, studies) send only the entry of a bar that raised both, the close journaled or listed as no signal with why (`settled` in `src/ta_engine/signals.py`); the web server's store does not let a `close-position` replace an entry of the same `signal_timestamp` (`SignalStore.upsert`, TradingView's alerts), while an entry still replaces a close. The scheduler's close is stored under `n/a`, apart.
- **Position Monitor** uses Saxo WebSocket streaming (replaces old 7s REST polling). Still consumes `trading-ops` for `daily_stats` and fallback `check_positions_on_saxo_api`.
- **Stream reader and position checks are decoupled.** `SaxoStreamClient` only merges deltas and flags a change; a separate task calls the callback with the latest snapshot (updates during a slow callback are coalesced). Don't await slow work in the receive loop.
- **Closures are recorded in the background** (`_record_closed_position_in_background`); `_closing_position_ids` keeps a position from being sold twice meanwhile. DB↔Saxo reconciliation (`StreamPositionHandler`) runs when a position leaves the stream and on a timer, not per tick.
- **A sale is kept until Saxo no longer lists the position** (`src/trade/close_intents.py`, pure, in `AsyncPerformanceMonitor`): an exit decided, a close asked from the admin (`request_close`), and what the trader could not sell (`not_closed` of `close_managed_positions_by_criteria`, handed over as a `close_position` ops message with its `reason`, `src/trade/ops_queue.py`) become intents, tried again with growing waits (`retry_after`), said on Telegram less and less often (`ALERT_GAPS`), ended when the position leaves the stream. A first, urgent attempt (a threshold just hit) asks nothing of Saxo before its sale; any other first looks for a sale already working at Saxo (`get_open_orders`) and waits for it: a second sell is refused (`SellOrdersAlreadyExistForOwnedContracts`). The monitor tries them every second (`keep_flat`, on the stream's last snapshot): an issuer that stops quoting brings no stream update. A close never skips a position in silence: `CanBeClosed: false` is `not_closed`, a position Saxo does not list `not_listed`, journaled as such.
- **Nothing is held after the day's close nor into a US release**: from `close_position_time` + 60 s until the next day's `trading_start_hour` the monitor sells what it still manages (`END_OF_DAY_REASON`, said once per position), and from the `macro_news` rule's `flatten_minutes_before` a release until its window ends (`flat_window_at`, reason `Flat before CPI (14:30)`, mirrored by the simulator, `tests/test_backtest_parity.py`). Entries are refused from the earlier of the two starts (`NewsRule.window`). Two Friday positions were held over the weekend (18 Sep, 9 Oct 2026) and a long held through the CPI of 14 Oct, unquoted for 250 s, was sold at −30 %.
- **A position just bought is judged from Saxo's next quote** (`src/trade/fresh_quote.py`, pure, shared by the monitor and the simulator; `position_management.wait_for_fresh_quote`, on unless false, checked by `ConfigurationManager`): Saxo quotes a turbo about every 30 s (40 at the 95th percentile, 13-20 Oct 2026) and fills an order at the live price, so the bid standing when a position appears is often older than its purchase. A position first seen within `FRESH_AFTER_SECONDS` (120) of its opening (`PositionBase.ExecutionTimeOpen`) is not judged on its bid until that bid changes: no stop, take-profit, trailing stop or daily target, its best result not raised; what comes with time (the day's close, a US release) is sold whatever the quote. A position whose opening is unknown is judged at once, as before. On 19 Oct 2026 a stop was "hit at -8.47 %" on a bid 17 to 27 s older than the purchase and sold at +0.51 %; six daily targets were "met" 1 to 6 s after a purchase and sold at a loss.
- **Every order request carries its own `x-request-id`** (`with_request_id`, the id it is kept under in `order_request`): Saxo refuses an identical order request within 15 s (409) unless each has its own, and a sale tried again is identical. The async client sends the same id again after a 429.
- **Saxo takes one order a second per session** (developer.saxo's rate limiting: `SessionOrders`): the async client spaces its order requests (`is_order_request`: POST, PATCH or DELETE on `/trade/v2/orders`, not the precheck) `ORDER_SPACING_SECONDS` apart (`OrderPacer`, `src/saxo_openapi/async_client.py`), and a refusal (429) is waited as the limit that ran out says (`wait_after_refusal`: `X-RateLimit-SessionOrders-Reset` for an order, the session's reset otherwise, never the app's day) then asked once more. Until v0.48.0 an order refused for the order limit waited the 60 s default of a missing `X-RateLimit-Session-Reset`: one order in ten of 27 Jul–26 Oct 2026 waited 60 s or more for Saxo's acceptance. The services share one session: the pacer is per process, so two services ordering in the same second can still be refused, and wait about a second.
- **A position WATA bought but lost is managed again** (`adopt_lost_positions`, at each reconciliation): one Saxo lists for a minute (`ADOPT_AFTER_SECONDS`, the trader's look lasts about 11 s) with no row, whose `SourceOrderId` is a buy WATA sent (`order_request`, `AsyncDbOrderRequestManager.purchases`), gets its row (`lost_position_row`, as `execute_trade_signal` writes it). One not bought by WATA is named once and left alone.
- **A position WATA sold keeps its reason** even when the reconciliation records it first (its 3 s settle is shorter than the bookkeeping's 7.5 s): `sync_db_positions_with_api` takes the reason of WATA's accepted sale (`sale_reasons`) and labels `SaxoAPI` only what WATA did not sell, as the simulator labels a knock-out. 43 of 245 closes of 2026-07-25 → 10-24 were mislabelled so.
- **The trader and the position monitor beat every 15 s** (`service_heartbeat`, `src/heartbeat.py`, written in the background, never in a trade's way): the admin's health judges them by it (`trader_health`, `position_monitor_health`, `with_heartbeats` in `src/admin/health.py`; a monitor without a consumer on `trading-ops` stays down), the log line and the queue consumer remaining for a service of before. No beat for 90 s is down.
- **The trader watches itself** (`src/trade/trader_watch.py`, from the keep-warm loop): a web server it cannot poll for a minute, no signal for `reporting.signal_silence_minutes` in trading hours (off unless set; `TradingRule.in_trading_hours`, no log line), Saxo refusing to renew the login (`SaxoAuth.last_refresh_error`: Saxo's answer is kept, a 429/5xx or no answer tried again twice), and the level Saxo serves the session at (`/root/v1/sessions/capabilities` every 5 min: below `FullTradingAndChat` Saxo gives delayed prices, and SaxoTraderGO takes the full level). With `trade.config.saxo_session.full_trading_level` (off unless true) the trader asks for that level (`PatchSessionCapabilities`, `PATCH`, 202, applied shortly after, read back 10 s later) and reads it every minute: one session of an account holds it, the last to ask, so another session (SaxoTraderGO, which may be logged off) taking it is said and the level asked for again; a refusal is said every 15 min and is a warning in health. The services share one login, so one session: the position monitor's and the recorder's prices come at the level the trader got. Saxo flagged no recorded quote as delayed (`DelayedByMinutes`, 0 in 1.79 million bars of 13-24 Oct 2026) while the session was at OrdersOnly; the turbos were quoted about every 30 s. While Saxo refuses to renew the login no new position is taken (`login_refusal`, right after the pause; on the dashboard tile through the overview's `saxo_login`; not in the backtests, which have no login).
- **No turbo is bought on a quote Saxo says is delayed** (`delayed_minutes` in the selection's filters, `no_market_reason` says so).
- **The widest spread bought** (`trade.config.turbo_preference.max_spread_percent`, no limit unless set): `filter_items_within_spread` leaves out, after the price range and before `select_best_price_candidate`, the turbos whose spread is wider than that share of their ask, on both live paths (`_find_turbos_uncached`, `build_selected_turbo_from_candidate_snapshots`, which the watchlist manager calls too, reading the setting itself) and in the backtests (`select_turbo`, `NO_TURBO_WITHIN_SPREAD`). With none left, the refusal names the narrowest spread seen (`no_turbo_within_spread`).
- **One source of signals per index** (`trade.config.signal_sources`, `src/trade/signal_sources.py`): TradingView's alerts unless the index is set to `engine`. The web server takes no webhook for an `engine` index (answered `ignored`, counted by `IgnoredWebhooks`, served on `/internal/webhook` with the sources it runs with, which the admin's Signals page and health read through `WataServices.webhook_state`); the TA engine refuses a live rule's signal for an index that is not (`NOT_SOURCE`, journaled, counted by `refusal_reason`); going live needs the web server to run with the index set to the engine, a hard requirement of `_check_can_go_live` that "Go live anyway" does not skip. `/internal/signal` (the scheduler's close, the admin's signals) is taken whatever the source. Both feed the one store, which keeps the newest signal of each index: TradingView's alerts and a live rule on one index would close each other's positions. Health warns of an `engine` index with no live rule (`unattended`) and of a live rule on an index that is not (`unheard`); the save preview (`checks.warnings`, given the live indices) says the same of a change.
- **The account guard** (`risk_management.pause_below_balance_eur`, `pause_after_drawdown_percent`; `src/trade/account_guard.py`, off unless set): below the floor, or that share under the highest since entries were last resumed, new entries are paused as the operator pauses them (`entries_paused_since`, plus `entries_paused_by_account_guard`), said once on Telegram, refused since as "paused by the account guard", resumed by the operator alone (the admin's resume also writes `entries_resumed_at`, from which the highest counts again). The value is Saxo's `TotalValue`, noted by `AsyncPositionService` from the balance it reads anyway (`last_total_value`): on the keep-warm timer, where `guard_account` runs between signals, and before an entry (`check_account_guard`, right after `check_entries_paused`; `AsyncTradingOrchestrator.account_value` reads the balance again only when the last is older than `ACCOUNT_VALUE_FRESH_SECONDS`). The highest is the larger of `account_balance_history`'s daily values recorded since the resume (`highest_since`) and those the trader read since its start. Mirrored by the backtests (the simulator's account value, cash and positions at their standing bid, and its highest; a trip refuses every later entry of the run) and the dashboard (the pause said to be the guard's).
- **The day's breakers** (`risk_management.max_consecutive_losses`, `max_drawdown_from_day_best_percent`; `src/trade/day_breakers.py`, off unless set): on the day's closed results in the order they closed (`get_today_closed_results`), no new entry for the rest of the day once that many lost in a row, or once the day's compounded result is that many points under its best at a close (0 before the first). One pure module for the trader (`check_day_breakers`, after `check_max_trades_per_day`), the backtests (`entry_refusal`'s `day_results`) and the overview (`breakers`, the figures the Next entry tile compares with the limits).
- **A silent position stream is replaced by REST** (`StreamPositionHandler.check_stream`): managed positions open, in trading hours, and nothing from the stream for 15 s, their exits are checked through `check_all_positions_performance` every 5 s, said after a minute. The stream client takes its token in a thread (`_current_token`): a renewal is a request to Saxo, a lapsed login a wait for its code, and its loop is the monitor's.
- **A service stops cleanly on Docker's stop** (since v0.40.0; before, every stop was a kill after 10 s): `exec` in `src/start_python_script.sh` and `init: true` on every WATA service of the compose file hand SIGTERM to Python (tini as PID 1; a shell in between never passed it on, and a Python of PID 1 ignores what it has no handler for). The trader finishes the signal in hand and polls no more (`stopping` of `poll_and_dispatch_signals`, `stop_grace_period` 60 s): cut off between Saxo taking an order and WATA writing it down, a position would have no row, and nothing would adopt it. The position monitor starts no sale and waits for the one under way (`StoppableMonitor` in `src/position_monitor/__init__.py`, kept out of `src/trade/async_services.py`, which every backtest's code digest holds; `stop_when_asked`; 45 s), its loops cancelled only then. The scheduler leaves its loop between two jobs. The uvicorn services, the recorder, the feed and the TA engine stop with the handlers they had. CI stops the scheduler's container and reads its line (`A service stops at once and cleanly on Docker's stop`).
- **No secret in a log line** (`src/logging_helper/redaction.py`): each handler `setup_logging` installs cleans every line (`RedactingFilter`) of the shapes of secrets (a token in a query, a Bearer header, the stream's `authorization=BEARER%20…`, Telegram's `/bot<id>:<token>`, `AccountKey=`/`ClientKey=` and `AccountKey: …` in a body or a message, a password in an address) and of the values registered with `register_secret` (the configuration's secrets, the webhook token, Saxo's tokens, Saxo's account and client keys, Capital.com's login, the heartbeat URL), registered where a service reads them (Saxo's keys in `get_account_info_async` and the watchlist manager's `get_account_key_async`); a value is taken for a secret only when it looks like one (8 characters and not a plain word under 16). Until v0.59.1 the trader's start line wrote Saxo's keys (`Account: <key>, Client: <key>`): that shape stays among the patterns, for the files the Logs page still reads. uvicorn's own lines go through `uvicorn_log_config()`, whose access filter cleans the path alone (its formatter needs the five arguments). `httpx`, `httpcore` and `websockets` stay at WARNING whatever `logging.level` says: they name whole addresses. The admin's Logs page shows, and searches, lines cleaned the same way.
- **The bot answers commands, and only reads** (`src/mq_telegram/commands.py`, `updates.py`; `reporting.telegram_commands`, off unless true, checked by `ConfigurationManager`): `/status`, `/positions`, `/day`, `/signals`, `/help`, read with getUpdates in a thread of the telegram service beside the queue's consumer. Only the chat the bot sends to is answered (another is passed over without a word), a command once (none older than 2 min, none past 6 a minute), in one message, and only getUpdates and sendMessage are asked of Telegram. Each command opens its own connection with `default_transaction_read_only` and runs only the SELECTs of `STATEMENTS`; the reasons the services wrote are cleaned as log lines are, long numbers taken out, and no answer names an id, a key or a token. Nothing there pauses, resumes, closes, restarts or changes a setting or a rule, and nothing is published to a queue: `tests/test_telegram_commands.py` holds the two files' imports (pure modules of `src/trade` and the redaction alone, no pika), the statements, and the chat; `tests/test_infrastructure_live.py` runs them on a real schema and sees a write refused.
- **An alert does not need the server's queue, nor the server**: `AsyncTelegramSender.send` sends to Telegram's Bot API itself when RabbitMQ refuses (the bot token never logged); `WATA_HEARTBEAT_URL` (`.env`, the position monitor's container alone) is an outside dead-man's switch, pinged every minute while the stream is heard (`stream_heard_lately`), never logged.
- **The US market's holidays and early closes are a file** (`src/trade/data/us_market_calendar.csv`, each row the official page it was read from, NYSE's days that Nasdaq keeps; `src/trade/market_calendar.py`): the trader takes no entry on a closed day, and on an early close none from the early close less its risky minutes (`entries_end_moment`); the scheduler (`job_early_close`) and the monitor's end of day sell as long before it as `close_position_time` is before `trading_end_hour` (`sale_moment`, `TradingRule.sale_moment`). Mirrored by the backtests (`entry_refusal`'s `market_calendar`, `closing_signals`; its digest in `made_with.market_calendar`) and the dashboard tile (the overview's `market_day`). `market_closed_dates` still applies. The file holds whole years: from 30 days before its end the scheduler says so each morning and health warns; keep it ahead.
- **Trading hours may be New York's** (`market_hours.timezone`, the trading timezone unless given, checked by `ConfigurationManager`): the trading and risky hours and `close_position_time` are read in it (`TradingRule.market_timezone`, the scheduler's close, the monitor's end of day, the backtests' `market_timezone`, the tile's `limits.market_timezone`, the price recorder's `is_trading_time`, the admin's `trading_hours` for downloads, paper days, the research export and the MCP's market), while days are counted in the trading timezone (`trading_timezone` in `src/admin/downloads.py`; a run's days are Paris days), so that the US session's hours hold the weeks Europe and the US change clocks apart. In those weeks, 02:00 in New York is 07:00 in Paris, an hour before Saxo quotes the turbos: an entry then finds none. The risky minutes run from their hour and minute to the end of the day (`(hour, minute) >= risky start`): counting the minute alone in each hour left holes in a window over an hour.

- **`requirements.txt` is the whole environment**: every package installed is a line of it at one exact version, and every line is installed. A job builds the images with the server's own script (`docker_build.sh`) and checks the Python it gets. Libraries are installed before the code is copied and only from ready-made builds (`--only-binary=:all:`): the image is built on the server beside the running containers (nothing stops for it), so whatever the build downloads or compiles takes processor time from the trading services, a minute for a release that changes libraries.

One that does not stay up goes back to its image of before and the rest waits; one not seen at work stops the rest and stays. `history.jsonl`, `status/status.json`.

A read of one instrument goes through the key; a read of a period across instruments (the research export's day, Availability, `wataprices export`, the lab's reload of a day) goes through the BRIN index on `ts` (`idx_price_bar_10s_ts`, 32 kB a month), which the recorder builds at its start: 0.5 s for a month of 4.8 million bars, under the pool's 30 s `command_timeout` (a start that fails exits, and its bars are lost). - **The backtest repeats WATA's rules** (`src/backtest/rules.py`, `simulator.py`): the trader's checks on an entry, in `handle_trading_signal`'s order (an entry refused closes nothing; with a cash reserve, an entry that failed still sells the other side, `_sell_after_failed_entry`); the orchestrator's sizing (`_calculate_position_scale`, `_calculate_bid_amount`); the position monitor's exits (`AsyncPerformanceMonitor._evaluate_positions`, with its reason strings, which `src/admin/analysis.py` groups as the Exits page does; the sale before a release, `news_flatten_minutes_before`); the scheduler's close of the day; the window around US releases (`news_*` settings read from the `macro_news` rule, the calendar handed to `entry_refusal`). - **A turbo's price at a moment is the open of the ten-second bar that starts at or after it** (`ceil10`, `TurboSeries.quote_at` in `src/backtest/data.py`). `BarBuilder` makes a bar for every bucket while the feed is alive, so the price is at most ten seconds late and never early. No bar while the recorder listened (`price_recorder_coverage.feed_ok`) means not quoted. A turbo never quoted again that day, its bid under a quarter of its high, is knocked out and sold at 0 (`SaxoAPI`). Inside a bar the monitor sees open, low, high, close (high before low when it closed lower), `RangeBarBuilder`'s order; how a stop crossed inside ten seconds fills is a setting (`stop_fill`). The trader is sequential: a signal is decided once the orders of the one before are filled.

Of WATA's 31 purchases of 13-20 Oct 2026, the standing ask was 0.48 % under the price paid on average (8.3 % on 19 Oct), the next one 0.04 %. A sale by a signal, the day's close or before a release likewise; an exit of the monitor sells at the bid that decided it. Measured fills keep the quote when the order left plus a drawn slippage, what their measure compares (`Simulator._next_quote`). The simulator judges a position as the monitor does (`wait_for_fresh_quote`, from the live configuration; off for the runs made before), parity tested: with `next` and the wait off, a run replays the monitor of before, its false exits included. A fill 1 % or more from the standing quote is said in the trade's notes.

The database down, the list still gives the files (`saxo_error`).

- **The TA engine is opt-in** (compose profile `ta` + `trade.config.ta_engine.enabled`, checked by the engine as the feed checks its section) and outside the trading path.

  - It builds bars by the admin charts' rules (`src/ta_engine/bars.py`, `RangeBarBuilder` unchanged).
  - It evaluates each new bar by continuing the rule's run (a load asked `continued`, `Runner.continueRun` in `runnerCore.ts`): the new bars go into the PineTS of the last run (`_appendCandle`) and run on its context (`_executeIterations`), as a whole run runs its last bar, so a bar's alerts are a whole run's. On the user's R60 script, 0.3 ms a bar against 2 s for a whole run of its 9,476 bars of a day (measured 2026-10-23 on the Mac, identical alerts). Its alerts and its plots (keyed as PineTS keys them) at the bars since the last check are compared; the same, the next bars continue the whole run's context. Different, or a whole run that fails where the continued one went on, and the rule runs whole until the engine starts again (said on Telegram, the run's `whole` in its state). A runner that ended while it held continued runs runs its rules whole until the next restart_time (`RunnerSlot.whole_until`).

A change of it loads the rule again (`RUN_FIELDS`). The rule's dialog counts the bars they make (`GET /api/ta/history`, `src/admin/ta_history.py`): the engine's own builders on the feed's rows from the rule's start, those closed by the last restart and by now, and each engine day of the week. A change to where the engine starts a rule's bars or how it builds them (`last_restart`, `rule_anchor`, `_builder` in `engine.py`) is made there too: `tests/test_admin_ta_history.py` holds the count to what the engine loads.
  - Before sending: the rule is live in `rules.json` now and alone on its indice, which takes the engine's signals (`trade.config.signal_sources`, given to `Engine` by the service: `src/ta_engine/settings.py` is in the backtests' code digest); the action is `long`, `short` or `close-position`; the bar closed less than `max_signal_age_seconds` ago; the feed is not stale.
  - A signal is journaled first (`ta_signal`, unique on rule, bar and alert): nothing is sent twice, and a history loaded after a restart is never sent.
  - `signal_timestamp` is the close of the bar, since the web server keeps the newest signal of each indice.
- **The Pine runner is confined** (`src/ta_engine/runner.py`):
  - `node --permission --allow-fs-read=<its folder>`, `env={}`, `--max-old-space-size`, and a time limit per request;
  - inside, every import is refused once it has started (`module.registerHooks`), and the network globals and `process.kill` are taken away. Node 24 has no permission for the network: this stands for it;
  - `node_path` and `rules_path` are not settings, since the admin edits `trade.config`.
- **The engine measures itself, for the Engine monitor** (`src/ta_engine/monitoring.py`, tables `ta_engine_tick` and `ta_rule_run`; the page is `/ta/monitor`, `src/admin/ta_monitor.py`):
  - `TickMark` and `RunMark` are set by plain assignments as the tick goes, and handed over once it is done, every signal sent (`tick()` wraps `_tick`, which the tests call through it). Nothing is awaited for them between a run and its signals. A run that continued its rule's run says so in its row's `figures` (`continued`); a check is a `CheckMark` in its tick's `figures.checks` (a check and an append of one rule share a tick, and `ta_rule_run` has one row per rule and tick).
  - One task writes them in the background, a batch at a time; no asyncio lock or event (the tests run the engine in several loops). A database too slow to take them makes the engine drop them, an hour of ticks waiting at most, counted in `ta_engine_state.figures.monitoring`; never a signal (tested).
  - Kept `trade.config.ta_engine.monitoring_days` (7, 1 to 30): the engine removes the older rows at its start and after each daily restart, a day at a time, the cutoff computed in Python. The admin's pool is read-only: only the engine can.
  - A signal's run is its rule's whose `tick_at` is the signal's `raised_at` (both `_moment` of the tick's `now`): the delivery steps join them so, then `signal_journal` and `order_execution`, all on the server's clock.
  - The runners', the engine's and the container's memory are read from Linux (`/proc/<pid>/status`, cgroup v2 through `cgroup_memory` in `src/price_history/process.py`): None elsewhere.
  - The checks of the last 15 minutes fail at half of a limit WATA already has (`max_signal_age_seconds`, `run_timeout_seconds` or the bar, the 10 s tick, `stale_feed_seconds`, 85 % of the container), and when a live rule's continued run differed from a whole run. The feed's leaves out the engine's first tick after a start (`figures.first` of its row): a deploy stops the feed with it. The ticks' leaves out those that loaded a rule or checked a continued run (`_STEADY` in `queries.py`): a whole run more, by design. Health turns the TA engine's OK into a warning with the first that failed, only for what can cost a live signal (the live runner, live signals); `/api/ta/engine` says the same (`ta_engine_health`).
  - The refusals are counted by the start of the engine's own texts (`NOT_ALONE`, `NOT_SOURCE`, `TOO_OLD`, `STALE_FEED`, `NO_SENDER`, `NOT_TAKEN` in `engine.py`, `CLOSE_WITH_ENTRY`): a change to one is made in `refusal_reason` too (tested together), and each begins with fixed text, the start being what is matched. The new tables are never exported for research (`test_research_export.py`).
- **Going live is an operator action** (`POST /api/ta/rules/{id}/mode`). It needs:
  - `require_actions_enabled`;
  - the indice in `allowed_indices`;
  - the indice taking the engine's signals as the web server runs (`trade.config.signal_sources`, read through `/internal/webhook`): not skipped by `force`;
  - the epic recorded by an enabled Capital.com feed;
  - one live rule per indice, an alert that makes a signal, and the pinned files as their sha256 says;
  - its readiness (`unmet_readiness` in `src/admin/ta_readiness.py`, which the page's `readiness.ts` mirrors with `holdingBack`: a change to one is made in the other): a week of weekdays in shadow (from the later of its move to shadow and the last change of what it runs: `run_changed_at`, which `RuleStore.update` writes when one of the engine's `RUN_FIELDS` changes, whoever changed it), a signal journaled, no day on paper outside its reference run's range, the engine running it without fault. A rule short of one goes live only with `force` (the confirmation's "Go live anyway"), and its audit entry says what was missing.

  It is audited (log, audit file, Telegram), and so is a change to a live rule. Leaving live is always allowed, and audited. A live rule cannot be deleted, nor can a script or a library a rule pins.

- Pine studies: `python -m src.research.study` as a child of the admin (`src/admin/studies.py`), one at a time. `npm run build:runner` and `npm run build:checker` in `admin_ui/` make what they run.

The six tools that run a study are `research_tool(..., jobs=research.jobs)`: done within 45 s they answer as before, otherwise they hand back a job (`src/admin/mcp_server/jobs.py`), which `job_wait` answers; the work goes on whatever becomes of the request, a job is the token's own and kept 15 minutes after it ends.
- **The journal counts trials made elsewhere** (`ExperimentJournal.record_trials`, a `trials` event; MCP `exp_trials`, the lab's `exp trials`): a port screened on the Mac, by hand. They count in the family's trials, so in later sweeps' `trials_before`, and are listed apart (`elsewhere`), never as a run.
- **The day budget counts trading days** (`guards.trading_days`: weekdays outside the live closed dates, DD/MM/YYYY as the trader reads them), in `backtest_start` and every kind of `backtest_derive`.
- Answers are held to what fits: `pine_run` lists the alerts asked for (`alert_titles`, `max_alerts`, every one counted by title) and, still over 32,000 characters, thins its plots' points, then cuts the alerts listed, saying so (`fitted` in `tools/pine.py`), `pine_compare` its rows when asked (`rows`), `backtest_trades` its candidate turbos when asked; `data_bars` as CSV gives up to a week of bars (70,000, 8 MB, under the 16 MiB Claude Code reads).
- **The AI agent's memory is read here, never changed** (`tools/memory.py`: `memory_list`, `memory_read`, through `ResearchServices.memory`, which is `ctx.agent_memory`; `src.admin.agent_memory` is in the boundary's allowlist, and `tests/test_mcp_tools_memory.py` holds a store whose changes are tripwires). A read notes its caller on the entry (`read_by`): the token's name, or `agent:<conversation>`.
- Claude's shadow rules (`shadow.py`): its own, never live; the only `set_mode` call in the endpoint is `ShadowRules._switch` (tested). Each is run first on its own history, and refused over `admin.mcp.shadow_day_ms` an engine day (2 s by default, 500 to 10,000: the operator's to raise).
- Numbers come back to six significant digits but three decimals at least (`compacted` in `shape.py`): six digits of Dukascopy's 29143.543 were 29143.5, which hid the decimal its range bars count in.
- The TA engine runs live and shadow rules on two runners (`src/ta_engine/engine.py`); given one runner, it runs every rule on it as before.

No text under `src/admin/agent/` may read like an SQL write in capitals: `test_the_admin_writes_five_tables_and_no_other` reads every file of the admin.

## CI / Deploy

- **CI**: GitHub Actions (`.github/workflows/ci.yml`), on push/PR to main. Five jobs: `tests.sh` on each Python of the matrix; the image built for each, with the Pine runner built into it first, `python -m src.release.check` run inside it (what the install checks: every service loads, the libraries, the validators, the runner confined) and the manifest read inside it as the server reads it; the images built by the server's own `docker_build.sh`, with a toy compose project on real Docker where one pinned container is recreated alone and the other untouched; the live tests against PostgreSQL and RabbitMQ; the admin interface. `tests/test_deploy_compose.py` keeps the workflow, the `Dockerfile` and the compose file saying the same thing (the Python of the image is in the matrix, the live tests get the compose file's images)

- **Deploy**: `./deploy_app_to_your_server.sh` from `deploy/tools` (Ansible playbook `deploy_app.yml`): installs the release beside what runs (nothing stops), says the plan, then applies what may go now (`watadeploy apply`); what is held back waits for `watadeploy apply` or the System page. `-e apply=none` installs only, `-e services=...` applies those, `-e force=true` whatever holds them back, `-e full=true` stops and starts everything (infrastructure changes)
