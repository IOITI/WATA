# WATA — AGENTS.md

## Project

Automated trading assistant for Saxo Bank Knock-out warrants (Turbos). Python 3.14, FastAPI, async microservices in Docker.

## Service map

| Role               | Entrypoint (`__init__.py`) | Communicates via                          |
|--------------------|-----------------------------|-------------------------------------------|
| `web_server`       | `src/web_server/`           | FastAPI on `:80`, query-param token auth  |
| `trader`           | `src/trader/`               | HTTP-polls web_server `/latest-signals`   |
| `position_monitor` | `src/position_monitor/`     | Saxo WebSocket streaming + `trading-ops`  |
| `scheduler`        | `src/scheduler/`            | Publishes to `trading-ops` / web_server   |
| `telegram`         | `src/mq_telegram/`          | Consumes `telegram` queue                 |
| `watchlist_manager`| `src/watchlist_manager/`    | REST API on `:8081`                       |
| `admin`            | `src/admin/`                | FastAPI on `:8082`, cookie session; serves the React UI built from `admin_ui/` |
| `price_recorder`   | `src/price_recorder/`       | Own Saxo stream; writes PostgreSQL only. Nothing calls it |
| `capital_feed`     | `src/capital_feed/`         | Own Capital.com stream; writes PostgreSQL, publishes live prices to RabbitMQ `wata.prices`. Nothing calls it |
| `ta_engine`        | `src/ta_engine/`            | Reads the Capital.com feed's tables; runs the signal rules' Pine scripts in a confined Node child; POSTs live rules' signals to web_server `/internal/signal` (Bearer). Nothing calls it |

Each service runs as a Docker container; `WATA_APP_ROLE` env var selects which `__init__.py` runs via `src/start_python_script.sh`.

## Infrastructure

- **RabbitMQ** — queues: `trading-signals` (trade actions, no longer consumed), `trading-ops` (ops/daily_stats), `telegram_channel` (notifications); topic exchange `wata.prices` (the Capital.com feed's live quotes and bars, transient, read by the admin while a chart follows them)
- **PostgreSQL 16** — replaces DuckDB (migrated in v0.7.0). DuckDB config is dead. Its container has 1536M, `shared_buffers` 512MB, `effective_cache_size` 1GB, `work_mem` 16MB and a `/dev/shm` of 256m (`command` and `shm_size` in the compose file, held by `tests/test_deploy_compose.py`), for a server of 8 GB: a change of them restarts the database, so it waits for a closed market.
- **Traefik** — reverse proxy, Let's Encrypt, TradingView IP allowlist
- **Config** — JSON at `WATA_CONFIG_PATH` path, validated strictly by `ConfigurationManager`

## Testing quirks

- **`WATA_CONFIG_PATH` must be set** before importing `src.web_server` (tests set `os.environ["WATA_CONFIG_PATH"] = "tests/test_config.json"`)
- Test config at `tests/test_config.json` — omit `day_trading` rule if testing with `trading_mode != "day_trading"`
- `tests/test_web_server.py` patches `verify_token` and `Request.client` for IP filtering tests
- `tests/test_config.json` uses minimal rule set; adding more rules requires updating config
- Some tests run the real Pine runner and need Node 22+ on the PATH (Node 24 through nvm) and `runner.mjs` built; they are skipped otherwise
- The tests replace PostgreSQL with fakes that only record the SQL text. New SQL can be run for real without Docker: `pip install pgserver asyncpg` in a throwaway virtual environment gives a PostgreSQL 16 in a folder (`pgserver.get_server(path).get_uri()`), which `PostgresConnectionManager`, `init_schema` and the managers accept as they are
- **`tests/test_infrastructure_live.py` is the database and the queue for real**, through the services' own code. It is skipped unless given `WATA_TEST_POSTGRES_DSN` and `WATA_TEST_RABBITMQ` (`user:password@host`), and must be run on its own: in a run of all the tests, other files have already put an empty module in the place of `asyncpg` and `aio_pika`. CI runs it against a PostgreSQL and a RabbitMQ of its own. Only for ones that can be thrown away: its messages go to the queues the services read
- **The stream client's connection is tested against a WebSocket server on the machine** (`LocalSaxoStream` in `tests/test_saxo_streaming_client.py`): opening, reading, Saxo dropping the connection, coming back with the last message read, leaving. Those tests are what says whether an upgrade of `websockets` keeps the position monitor's link to Saxo working: run them before and after one

## Architecture notes

- **Trader does NOT consume RabbitMQ** for trade signals — it long-polls `web_server:80/latest-signals` via `SignalPollingClient`. Old RabbitMQ `trading-signals` queue consumption was removed.
- **Signals are executed once.** The web_server store keeps the latest signal per indice until a newer one replaces it, so the trader dedups on `signal_uuid` (`select_signals_to_dispatch` in `src/trader/__init__.py`).
- **No entry around US releases** (the optional `macro_news` rule of `trade.rules`, off unless it is there): from `minutes_before` a release to `minutes_after` it (`minutes_after_fomc` for an FOMC statement, whose press conference follows), for the releases its `events` name. The calendar is `src/trade/data/macro_calendar.csv`, read by `src/trade/macro_calendar.py` (`NewsRule`, `window_at`, `refusal_text`): the trader reads it, so it lives on the trading side, and the backtests import it from there (never the other way). New York's hours, whatever either side's clocks. `TradingRule.check_macro_news` runs right after `check_market_hours`; an unreadable calendar never stops the trader. Past the calendar's last known day nothing is known and entries go on; from 30 days before it, the scheduler says so on Telegram each morning and the admin's health has a warning (`upkeep`). `ConfigurationManager` checks the rule only when it is there.
- **One moment, one trade: an entry wins over a close of the same moment.** An entry sells the other side before it buys, and a close taken after it would sell the position just opened. The TA engine and the replays (backtests, studies) send only the entry of a bar that raised both, the close journaled or listed as no signal with why (`settled` in `src/ta_engine/signals.py`); the web server's store does not let a `close-position` replace an entry of the same `signal_timestamp` (`SignalStore.upsert`, TradingView's alerts), while an entry still replaces a close. The scheduler's close is stored under `n/a`, apart.
- **Position Monitor** uses Saxo WebSocket streaming (replaces old 7s REST polling). Still consumes `trading-ops` for `daily_stats` and fallback `check_positions_on_saxo_api`.
- **Stream reader and position checks are decoupled.** `SaxoStreamClient` only merges deltas and flags a change; a separate task calls the callback with the latest snapshot (updates during a slow callback are coalesced). Don't await slow work in the receive loop.
- **Closures are recorded in the background** (`_record_closed_position_in_background`); `_closing_position_ids` keeps a position from being sold twice meanwhile. DB↔Saxo reconciliation (`StreamPositionHandler`) runs when a position leaves the stream and on a timer, not per tick.
- **Broker-side protective stop** (`position_management.protective_stop`) is opt-in and untested against Saxo; closes cancel a position's `RelatedOpenOrders` before selling.
- **Scheduler** sends `close-position` via HTTP POST to `web_server:80/internal/signal` (Bearer token), and `daily_stats` via RabbitMQ `trading-ops`.
- **Two auth schemes**: webhook uses `?token=...` query param; internal endpoints use HTTP Bearer token.
- **An access check reads the path from `request.scope["path"]`, not from `request.url`**: the URL is rebuilt from the `Host` header, which the caller writes. The web server's IP allowlist was skipped that way (`check_ip`, tested in `tests/test_web_server_advanced.py`).
- **`requirements.txt` is the whole environment**: every package installed is a line of it at one exact version, and every line is installed. The image is built on the server at each deploy, so a version left open would be chosen there, by pip, on the day (it was so for `h2`, `cffi`, `aiormq`…), and Dependabot does not check a line without one. A library added means its line and a line for each thing it needs that is not there yet: install the file in an empty environment and read `pip freeze`. CI fails when the two lists differ (`tests/requirements_lock.py`, a command that needs nothing but Python, tested by `tests/test_requirements.py`), on each Python and for each image; a library nothing imports any more must go, for the same reason.
- **The image's Python is the `ARG PYTHON_VERSION` at the top of the `Dockerfile`**, which the server builds as it is. CI tests that version and one other, and builds the image with each (`--build-arg`): the next one before a move, the one before for a while after it (3.12 today, the services having moved to 3.14 in v0.16.0). Changing Python is therefore two releases: the libraries brought to versions that run on both, then that one line. A job builds the image with the server's own command and checks the Python it gets. Libraries are installed before the code is copied and only from ready-made builds (`--only-binary=:all:`): the install script stops the application before it builds the image, so whatever the build downloads or compiles is time without trading.
- **A service runs its main coroutine with `event_loop.run(main())`** (`src/event_loop.py`): on uvloop, as the loop of that run alone. `uvloop.install()` goes through asyncio's policies, which Python 3.14 deprecates and 3.16 removes. The servers started by `uvicorn.run` get uvloop from uvicorn itself.
- **`websockets.connect` is the library's asyncio client** (the default one since websockets 14): a connection has a `state`, no `closed`, and `ConnectionClosed` says what was received in `rcvd`. `SaxoStreamClient` passes `proxy=None`: that client would otherwise look for a proxy in the environment, which the one before never did.
- **Schema** defined as plain dicts in `src/schema/__init__.py` (not pydantic), validated with `jsonschema`.
- **Admin is opt-in** (compose profile `admin`). It reads PostgreSQL through a read-only pool, reaches the other services through what they expose (`/latest-signals`, `/internal/signal`, watchlist endpoints, RabbitMQ, the Saxo token files) and has no Docker socket. Its only DB write is the pause of new entries (`trade_risk_state`, separate connection). All its outside access goes through `AdminContext` (`src/admin/context.py`), which tests replace with fakes.
- **What the trading services do for the admin** (all additive, none may block or fail a trade): the trader checks `TradingRule.check_entries_paused()` before opening and journals each signal's outcome in the background (`SignalJournal`, table `signal_journal`); the position monitor publishes `AsyncPerformanceMonitor.live_values()` to `position_live_value` on a timer and handles the `close_position` ops message (ignored when older than 60 s); both record the account balance with the daily report (`account_balance_history`) and keep what became of each order they send (`OrderTracker`, table `order_execution`).
- **An order's moments are marks in memory, written in the background** (`src/trade/order_tracker.py`): an `OrderTrace` is marked where the order leaves (`execute_trade_signal`, `_send_close_order`) and where Saxo is asked for its position (`find_position_by_order_id_with_retry`, `_fetch_and_update_closed_position`), and `OrderTracker.record` returns at once. Nothing may be awaited between the decision to sell and the sell, and `_track_close_order` must never raise: an error there would read as a sell that failed, and the position would be sold a second time (tested). The row is written twice, once Saxo has the order and once its outcome is known, by tasks that may finish in either order: the upsert never changes a row that has its outcome. The tracker also writes to `turbo_data_order` the orders nothing else records (a sell, a buy that gave no position); a buy that gave a position is written by the trade itself, as before. `order_time` is when the order left.
- **The admin reads an order with what became of it, its position and its signal** (`_linked_orders` in `src/admin/queries.py`), and falls back to the orders alone while a joined table does not exist yet. What the pages make of it (the steps, the sentences, the figures of a period) is `admin_ui/src/features/positions/orderLife.ts`, with its tests: two clocks are involved, the server's and Saxo's, and a step says which it was read on.
- **Every request to Saxo's order endpoint is kept with Saxo's answer** (table `order_request`): caught in `AsyncOrderService` (`place_market_order`, `place_related_stop_order`, `cancel_order_with_reason`), the only code that talks to that endpoint, so a new order path is recorded without asking. The caller says why in an `OrderContext` (purpose, position, signal, reason, the price it decided on); an `OrderRequest` is described just before the request leaves (plain assignments: nothing awaited, the rule of the sell above holds) and handed to `OrderTracker.record_request` once answered, which writes in the background and never raises. What is raised is unchanged: a refused order stays an exception for the caller, and is still not an order (`order_execution`, `turbo_data_order`). Saxo's answer is read from the `OpenAPIError` the client raised first (`describe_failure`): its code and message are under `ErrorInfo` for an order (`saxo_error_parts` in `src/trade/exceptions.py`), and which exception class the client raises still depends on the top-level code alone. The account's keys never reach the table (`without_account_keys`). The row is written once, its answer known: a service killed in between leaves none.
- **The admin shows what Saxo did not take as runs** (`refusal_runs` in `src/admin/order_requests.py`, pure): the attempts with one intent (selling a position, buying for a signal), ended by the request Saxo accepts or by five minutes without an attempt. A run carries the order's field names (`order_amount`, `instrument_price`...) so that the Orders table, its search and its export read both kinds of row; what the pages say of them is `admin_ui/src/features/positions/orderRequests.ts`, with its tests. `AdminQueries.open_positions` adds each open position's `sell_refusals`, and the event watcher announces their growth (`order_refused`), at most once a minute per position.
- **Admin config edits only touch `trade.rules`, `trade.config`, `reporting`, `logging.level`** (`src/admin/config_editor.py`); everything else is merged back from disk, on save and on backup restore alike (both go through `merge_editable`). `PROTECTED_PATHS` lists the infrastructure keys inside those sections (service URLs, listen address): a new key there that says where a service connects must be added to it. Services read the config at start, so a saved change applies at each service's next start. One section can also be saved alone from another page (`ConfigEditor.save_section`, only for `SECTION_PATHS`: the price recorder's, from its provider): it goes through `save`, so the same merge, validation, revision check, backup and audit apply.
- **Price recorder is opt-in** (compose profile `recorder` + `trade.config.price_recorder.enabled`) and outside the trading path: it reuses `AsyncInstrumentService.build_watchlist_candidates` and `SaxoStreamClient` unchanged, validates its own config section (`src/price_recorder/settings.py`, deliberately not in `ConfigurationManager`: a mistake there must not stop the trader), and creates its own tables (`PRICE_HISTORY_SCHEMA_SQL`, not part of `init_schema`). `BarBuilder` (`bars.py`) is pure and time-driven; the stream callback must stay memory-only. Lost bars cannot be re-fetched from Saxo, so a change that can drop them needs a test. Untested against Saxo.
- **Backtests trade the recorded turbos as WATA would have** (`src/backtest/`, outside the trading path: no trading service imports it). The signals are a Pine script's alerts, run as the TA engine runs a signal rule, or those WATA received (`signal_journal`). A simulated trader and position monitor buy and sell the turbos the price recorder kept, at their recorded ask and bid. An entry with no turbo recorded at that moment is not traded (`unpriced`), so a run covers only the days the recorder ran.
- **The backtest repeats WATA's rules** (`src/backtest/rules.py`, `simulator.py`): the trader's checks on an entry, in `handle_trading_signal`'s order (an entry refused closes nothing); the orchestrator's sizing (`_calculate_position_scale`, `_calculate_bid_amount`); the position monitor's exits (`AsyncPerformanceMonitor._evaluate_positions`, with its reason strings, which `src/admin/analysis.py` groups as the Exits page does); the scheduler's close of the day; the window around US releases (`news_*` settings read from the `macro_news` rule, the calendar handed to `entry_refusal`). The turbo is chosen by the live helpers themselves (`select_turbo` in `selection.py`). `tests/test_backtest_parity.py` runs the live code on the same inputs: a change to one of those must be made in the mirror too, or backtests describe a WATA that no longer exists.
- **A turbo's price at a moment is the open of the ten-second bar that starts at or after it** (`ceil10`, `TurboSeries.quote_at` in `src/backtest/data.py`). `BarBuilder` makes a bar for every bucket while the feed is alive, so the price is at most ten seconds late and never early. No bar while the recorder listened (`price_recorder_coverage.feed_ok`) means not quoted. A turbo never quoted again that day, its bid under a quarter of its high, is knocked out and sold at 0 (`SaxoAPI`). Inside a bar the monitor sees open, low, high, close (high before low when it closed lower), `RangeBarBuilder`'s order; how a stop crossed inside ten seconds fills is a setting (`stop_fill`). The trader is sequential: a signal is decided once the orders of the one before are filled.
- **A run or a study that dies says how and where** (`failure_of`, `failure_sentence` in `src/admin/backtests.py`, `StudyService._ending`): the exit's meaning (`exit_said` in `src/price_history/process.py`: −9 the kernel, −6 Node's full heap), the phase and day from `progress.json`, the engine day the runner was given with its bars and the runner's peak memory (`Progress.runner_day`, from `ReplaySession`'s `on_window`), the container's memory then and the kernel's OOM kills during the run (`memory.events`); in its status as `failure` and its error. The runner says its last stderr lines when it ends (`NodeRunner._last_words`), and the replay the engine day it was on.
- **Backtests asked for from the admin are child processes and folders of files** (`src/admin/backtests.py`, reached as `AdminContext.backtests`):
  - One at a time, at the lowest priority, `python -m src.backtest.run --run <folder>` reads the recorded turbos itself, a day at a time, through one read-only connection (`DatabaseData`: `default_transaction_read_only`, primary keys only). It writes under `admin.persistant.backtests_path/runs/<RUN_ID>/`, `summary.json` last.
  - A run id is made by the service and matched against `RUN_ID` before any path is built: keep it that way for every new route.
  - For a replay of the journal, the route reads it (`AdminQueries.journal_between`) and WATA's closed positions of the same days (`closed_positions`), and the service hands both to the child as files.
  - They change nothing live, so they are not operator actions (no audit entry, no Telegram), and have their own switch (`admin.backtests_enabled`). 92 days (731 on made-up turbos), 10 waiting and 3 h at most, one at a time: `admin.backtests_workers`, `backtests_max_queued` and `backtests_max_period_days` say otherwise, which only the lab does (4, 500, 731).
  - Tests give the service a fake launcher (`tests/test_admin_backtests.py`); one of them goes through a real child process on files (`FileData`: the export's columns and `instrument_id`, which the dev server writes too, `admin_ui/dev/fake_recorded.py`).
- **A Pine script is replayed by the TA engine's own code** (`ReplaySession` in `src/ta_engine/replay.py`, with the engine's runner): a window per engine day (restart to restart, bars from `history_days` before), alerts mapped to actions as a signal rule maps them, each reaching the trader `signal_delay_seconds` after its bar closed. Every window is loaded under one rule id (`REPLAY_RULE_ID`): the runner keeps what each id loaded, and compiles a script once while its source and inputs stay the same (`load` in `runnerCore.ts`). Each PineTS compile leaves about 60 MB of native memory that the process never gets back, outside V8's heap and so outside `--max-old-space-size`: a backtest that compiled its script at each engine day was killed for memory after 10 to 20 of them, each day slower. `python -m src.ta_engine.replay` prints the same signals.
- **A range is counted in the asset's own tick**: R60 is 6 points on Capital.com's US100 (a tick of 0.1), 0.06 on Dukascopy's (0.001: its files hold thousandths, and 6 points are R6000). The assets say theirs (`tick`, `tick_of` in `src/admin/prices.py`; MCP `data_assets`; the Backtests form under the range). Capital.com's day files name no instrument: a run on them takes the decimals its prices carry (`AssetRows._capital_decimals`), never Saxo's floor of two. An engine day of more than `MAX_WINDOW_BARS` (40,000) bars is refused before the runner is given it, saying the tick and what one point is (`too_large`, `built_bars` in `src/ta_engine/replay.py`, which builds a few rows at a time so as to stop early): the runner held 590 MB at 49,107 bars, and the backtests of R600 on Dukascopy (about 100,000 bars a day) were killed for memory.
- **A backtest is never read alone** (`src/backtest/baseline.py`, `figures.py`). The same days are traded again, 100 times by default, each day with as many entry signals as the strategy had, at random ten-second moments of its own hours where the recorder listened, long or short by a coin, on the same turbos and under the same rules. The summary says the share of those the run beat (`against_random`), how much it rests on (`sample`) and the range of its total with the days drawn again (`total_range`). The draws are seeded by seed, repetition and day, so two runs over the same days face the same random entries: keep them reproducible.
- **A sweep** (`src/backtest/sweep.py`): two axes and 64 combinations at most, an axis being a setting or a script input. The signals are made once per set of inputs; each combination is a whole simulation with its own account, its figures split at the first day held out. No random entries there; "Run this cell" makes a combination a run of its own.
- **A run starts with `DEFAULT_CAPITAL` (1,000 €) unless its changes say another** (`src/backtest/settings.py`): the live balance is not handed in (`ask_backtest`) but offered beside it (`options`' `capital.balance`; the form's "start from it", MCP `backtest_options`). At the live 21.82 € of 2026-10-21, 34 entries found no turbo to buy. Paper days use it too.
- **A setting added to a backtest needs a default that changes nothing** (`FIELDS`, `BacktestSettings` in `src/backtest/settings.py`, read from `config.json` as the services read it): a run keeps its settings as `settings.json`, read again by `from_dict`. A figure added to `summary.json` is absent from older runs: the pages take it as optional. A run records the code it was made with (`made_with.code`, `code_digest` over `_CODE` in `figures.py`), and the admin marks it stale when that differs: a file that decides a backtest's result and is outside `_CODE` must be added to it. Of `src/ta_engine`, `_CODE` lists the files a replay runs, not the live loop (`engine.py`, `monitoring.py`, `sender.py`, the service), whose changes leave runs as they were; `tests/test_backtest_code_digest.py` fails on a file of `src/ta_engine` the code listed imports (inside a function too) and `_CODE` leaves out.
- **A run's results are read beyond its total** (`src/backtest/robustness.py`, pure): risk figures on the daily results in `figures.risk` (Sharpe, Sortino and Calmar brought to a year only from 20 days, `ANNUALISED_FROM_DAYS`; time under water; the worst 5 % of days; payoff; the share of its best a winning trade kept), and in `summary.stress` the drawdown of the same days drawn again (seeded) and the total without the best days. A sweep keeps each combination's daily `curve`; its summary adds a walk-forward when asked (`sweep.walk_forward`: the best of the days before chosen again window after window, judged on the days after), the probability of overfitting (combinatorially symmetric cross-validation, from 8 days) and the deflated Sharpe ratio (from 20 days to choose on), with the trials made before counted (`sweep.trials_before`, which the lab passes from its journal). `tests/test_backtest_robustness.py` checks the deflated ratio against Bailey and López de Prado's own example.
- **A stress sweep is the run made again with worse fills** (`BacktestService.stress`, `POST /api/backtests/{id}/stress`): order time × slippage around the run's own (`STRESS_LATER_SECONDS`, `STRESS_WORSE_PRICE`), its own fills the first cell, `stress_of` in its request. It chooses nothing, so its summary has no overfitting figures.
- **The edge of the entries** (`src/backtest/edge.py`, `edge.json`, a headline in the summary): how the chart's asset moved 1 to 60 minutes after each entry signal, taken or not, signed by its direction, beside random moments of the same hour of the same day (seeded). The t-statistic is every signal's mean over its spread, only the signals whose windows do not overlap counted as observations. A run's, not a sweep's. The pages read it without its signals one by one (`BacktestService.edge`); the lab reads the file.
- **What kind of day each day was** (`src/backtest/regimes.py`, `days.json` `regime`): gap, range, realised volatility, trend or back and forth, the US open's first half hour, in the rules' trading hours of the chart's asset; groups in `labels` (volatility in thirds of the run's days). Each trade gets `session_part` and `minutes_after_open` (9:30 in New York, whichever city changed its clocks). The macro news come from `src/trade/data/macro_calendar.csv` (read by `src/trade/macro_calendar.py`, which the trader shares): each row names the official page it was read from (the Fed, BLS, BEA), the releases the 2025 shutdown cancelled are absent and the delayed ones at their day. It is not code: a run notes its digest and the day it ends (`made_with.calendar`) and warns past it. Keep it ahead: `python -m lab calendar check`.
- **Turbos made up from an index, for long histories** (`src/backtest/turbo_model.py`). A script that reads what a whole run gives otherwise at an earlier bar (`wholeBecause`, on its code without comments and strings: `barstate.*` but `isfirst`, `last_bar_index`/`last_bar_time`, `session.islastbar`, `timenow`, `math.random`, `request.*`, the visible range, a `strategy()`) is run whole over all its bars at each new one, as before. PineTS's `updateTail` is not used: it runs the last bar again as an open one, and in 0.11.1 raised none of the user's script's alerts and left `request.security` behind.
  - A continued run is checked against a whole run (`check`): at the rule's first new bar, then every `CHECK_SECONDS` (600), at the end of a tick that leaves the time it should take (its last whole run's, a quarter more), or anyway once `CHECK_SECONDS` late; one a tick, live rules first. Its alerts and its plots (keyed as PineTS keys them) at the bars since the last check are compared; the same, the next bars continue the whole run's context. Different, or a whole run that fails where the continued one went on, and the rule runs whole until the engine starts again (said on Telegram, the run's `whole` in its state). A runner that ended while it held continued runs runs its rules whole until the next restart_time (`RunnerSlot.whole_until`).
  - A held run keeps its memory (56 MB of heap for the user's rule at 9,476 bars): after a load or a check, past half of the runner's old space (`HELD_HEAP_SHARE`, measured after a collection the runner makes itself: `--expose-gc` set from inside, its `gc` in a context of its own that no script sees), the run of the most bars goes back to whole runs.
  - A rule may have its own `history_days` (0 to 30, `checked_history_days` in `src/admin/ta_rules.py`; kept in the rule only when it has one): fewer days for a script that needs little warm-up, which then runs faster at each bar. An epic's rows are kept from the earliest any of its rules needs (`Engine.anchor`), read back when a rule wanting more arrives, and each rule's bars start at its own (`rule_anchor`), as does a series it asks for (`request.security`, the rule being run is `_asking`). A change of it loads the rule again (`RUN_FIELDS`). A run made from a rule takes it as its `history_days` (the form's `withRule`, MCP `backtest_start`), and so does `python -m src.ta_engine.replay --rule`.
  - Before sending: the rule is live in `rules.json` now and alone on its indice; the action is `long`, `short` or `close-position`; the bar closed less than `max_signal_age_seconds` ago; the feed is not stale.
  - A signal is journaled first (`ta_signal`, unique on rule, bar and alert): nothing is sent twice, and a history loaded after a restart is never sent.
  - `signal_timestamp` is the close of the bar, since the web server keeps the newest signal of each indice.
- **The Pine runner is confined** (`src/ta_engine/runner.py`):
  - `node --permission --allow-fs-read=<its folder>`, `env={}`, `--max-old-space-size`, and a time limit per request;
  - inside, every import is refused once it has started (`module.registerHooks`), and the network globals and `process.kill` are taken away. Node 24 has no permission for the network: this stands for it;
  - `node_path` and `rules_path` are not settings, since the admin edits `trade.config`.
- **The engine measures itself, for the Engine monitor** (`src/ta_engine/monitoring.py`, tables `ta_engine_tick` and `ta_rule_run`; the page is `/ta/monitor`, `src/admin/ta_monitor.py`):
  - `TickMark` and `RunMark` are set by plain assignments as the tick goes, and handed over once it is done, every signal sent (`tick()` wraps `_tick`, which the tests call through it). Nothing is awaited for them between a run and its signals. A run that continued its rule's run says so in its row's `figures` (`continued`); a check is a `CheckMark` in its tick's `figures.checks` (a check and an append of one rule share a tick, and `ta_rule_run` has one row per rule and tick).
  - One task writes them in the background, a batch at a time; no asyncio lock or event (the tests run the engine in several loops). A database too slow to take them makes the engine drop them, an hour of ticks waiting at most, counted in `ta_engine_state.figures.monitoring`; never a signal (tested).
  - Kept `trade.config.ta_engine.monitoring_days` (7, 1 to 30): the engine removes the older rows at its start and after each daily restart, a day at a time, the cutoff computed in Python. The admin's pool is read-only: only the engine can.
  - A signal's run is its rule's whose `tick_at` is the signal's `raised_at` (both `_moment` of the tick's `now`): the delivery steps join them so, then `signal_journal` and `order_execution`, all on the server's clock.
  - The runners', the engine's and the container's memory are read from Linux (`/proc/<pid>/status`, cgroup v2 through `cgroup_memory` in `src/price_history/process.py`): None elsewhere.
  - The checks of the last 15 minutes fail at half of a limit WATA already has (`max_signal_age_seconds`, `run_timeout_seconds` or the bar, the 10 s tick, `stale_feed_seconds`, 85 % of the container), and when a live rule's continued run differed from a whole run. The feed's leaves out the engine's first tick after a start (`figures.first` of its row): a deploy stops the feed with it. The ticks' leaves out those that loaded a rule or checked a continued run (`_STEADY` in `queries.py`): a whole run more, by design. Health turns the TA engine's OK into a warning with the first that failed, only for what can cost a live signal (the live runner, live signals); `/api/ta/engine` says the same (`ta_engine_health`).
  - The refusals are counted by the start of the engine's own texts (`NOT_ALONE`, `TOO_OLD`, `STALE_FEED`, `NO_SENDER`, `NOT_TAKEN` in `engine.py`, `CLOSE_WITH_ENTRY`): a change to one is made in `refusal_reason` too (tested together). The new tables are never exported for research (`test_research_export.py`).
- **Going live is an operator action** (`POST /api/ta/rules/{id}/mode`). It needs:
  - `require_actions_enabled`;
  - the indice in `allowed_indices`;
  - the epic recorded by an enabled Capital.com feed;
  - one live rule per indice, an alert that makes a signal, and the pinned files as their sha256 says.

  It is audited (log, audit file, Telegram), and so is a change to a live rule. Leaving live is always allowed, and audited. A live rule cannot be deleted, nor can a script or a library a rule pins.

## Claude's MCP endpoint (`src/admin/mcp_server/`)

- `/mcp` of the admin, off unless `admin.mcp_enabled`; the SDK (`mcp==2.3.0`) is imported by `server.py` only, and only then. Never name a package `mcp` under `src/`: it would hide the SDK from every service.
- Bearer tokens made on the server (`watamcptoken` → `python -m src.admin.cli --mcp-token`); the file keeps sha256 only. `gate.py` refuses any `Origin`, throttles, answers 503 while paused (System › Claude).
- The tools reach the admin only through `facade.ResearchServices` (named queries, no pool, no trading service). `tests/test_mcp_server.py` holds the exact tool list, `tests/test_mcp_boundary.py` the import allowlist and the tripwires. A new tool needs both.
- Pine studies: `python -m src.research.study` as a child of the admin (`src/admin/studies.py`), one at a time. `npm run build:runner` and `npm run build:checker` in `admin_ui/` make what they run.
- **No call lasts 60 s**, after which Claude Code ends an HTTP request (unless the Mac's server entry sets `timeout`): tools answer within `TOOL_SECONDS` (50), `backtest_wait` waits 45 s at most. The six tools that run a study are `research_tool(..., jobs=research.jobs)`: done within 45 s they answer as before, otherwise they hand back a job (`src/admin/mcp_server/jobs.py`), which `job_wait` answers; the work goes on whatever becomes of the request, a job is the token's own and kept 15 minutes after it ends.
- **The journal counts trials made elsewhere** (`ExperimentJournal.record_trials`, a `trials` event; MCP `exp_trials`, the lab's `exp trials`): a port screened on the Mac, by hand. They count in the family's trials, so in later sweeps' `trials_before`, and are listed apart (`elsewhere`), never as a run.
- **The day budget counts trading days** (`guards.trading_days`: weekdays outside the live closed dates, DD/MM/YYYY as the trader reads them), in `backtest_start` and every kind of `backtest_derive`.
- Answers are held to what fits: `pine_run` lists the alerts asked for (`alert_titles`, `max_alerts`, every one counted by title) and, still over 32,000 characters, thins its plots' points, then cuts the alerts listed, saying so (`fitted` in `tools/pine.py`), `pine_compare` its rows when asked (`rows`), `backtest_trades` its candidate turbos when asked; `data_bars` as CSV gives up to a week of bars (70,000, 8 MB, under the 16 MiB Claude Code reads).
- Claude's shadow rules (`shadow.py`): its own, never live; the only `set_mode` call in the endpoint is `ShadowRules._switch` (tested). Each is run first on its own history, and refused over `admin.mcp.shadow_day_ms` an engine day (2 s by default, 500 to 10,000: the operator's to raise).
- Numbers come back to six significant digits but three decimals at least (`compacted` in `shape.py`): six digits of Dukascopy's 29143.543 were 29143.5, which hid the decimal its range bars count in.
- The TA engine runs live and shadow rules on two runners (`src/ta_engine/engine.py`); given one runner, it runs every rule on it as before.

## CI / Deploy

- **CI**: GitHub Actions (`.github/workflows/ci.yml`), on push/PR to main. Five jobs: `tests.sh` on each Python of the matrix; the image built for each, with the Pine runner built into it first, every service loaded inside it and the runner run there (`python -m src.ta_engine.runner`); the image built as the server builds it; the live tests against PostgreSQL and RabbitMQ; the admin interface. `tests/test_deploy_compose.py` keeps the workflow, the `Dockerfile` and the compose file saying the same thing (the Python of the image is in the matrix, the live tests get the compose file's images)

- **Deploy**: `./deploy/tools/deploy_app_to_your_server.sh` (uses Ansible playbook `deploy_app.yml`)
